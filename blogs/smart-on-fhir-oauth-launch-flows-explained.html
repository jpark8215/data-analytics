SMART on FHIR Explained: OAuth 2.0 for Healthcare Apps, Launch Flows, and Scopes Without the Jargon

SMART on FHIR is the security layer that lets third-party healthcare apps connect to electronic health records safely. This post explains the three launch flows with sequence diagrams, decodes the scope syntax, and walks through a real token request step by step.

Published: October 27, 2026

If you have spent any time building or integrating with electronic health record (EHR) systems, you have likely encountered the term SMART on FHIR. The documentation is thorough, the specification is well-maintained by HL7, and the concept is widely referenced in federal interoperability mandates. What is remarkably scarce, however, is a plain-language explanation that actually shows you how the pieces connect. This post is an attempt to fill that gap.

SMART on FHIR is not a single technology. It is a security framework that sits on top of two widely understood protocols: OAuth 2.0 (for authorization) and OpenID Connect (for identity). What SMART adds is a set of healthcare-specific conventions -- standardized launch flows, a defined scope vocabulary, and a discovery mechanism -- that allow any conformant app to securely connect to any conformant EHR without bespoke integration work. The official specification is maintained by HL7 as the SMART App Launch Implementation Guide, currently at version 2.2.0.

The regulatory importance of SMART on FHIR is also concrete. The 21st Century Cures Act prohibited information blocking by certified EHR vendors and required them to expose standardized FHIR APIs. The ONC Health IT Certification Program and CMS interoperability rules (including the CMS-0057-F Prior Authorization and Interoperability rule) specifically require SMART App Launch v2 as the security layer over those FHIR R4 APIs. If you are building a healthcare application that needs to access patient data held by a major EHR, you are building with SMART on FHIR whether you realize it or not.

The Foundation: How Discovery Works

Before any authorization happens, a SMART-enabled app needs to find the EHR's OAuth 2.0 endpoints. It does this through a standardized discovery document. Every SMART-compliant FHIR server publishes a JSON file at a fixed path relative to its FHIR base URL.

GET [FHIR_BASE_URL]/.well-known/smart-configuration

The response contains everything an app needs: the authorization endpoint, the token endpoint, the supported grant types, the supported SMART capabilities, and the algorithms the server accepts for signed assertions. A representative response looks like this:

{
  "issuer": "https://fhir.example.com",
  "authorization_endpoint": "https://fhir.example.com/oauth/authorize",
  "token_endpoint": "https://fhir.example.com/oauth/token",
  "capabilities": [
    "launch-ehr",
    "launch-standalone",
    "client-public",
    "client-confidential-symmetric",
    "sso-openid-connect",
    "context-ehr-patient",
    "permission-patient",
    "permission-user",
    "permission-v2"
  ],
  "grant_types_supported": ["authorization_code", "client_credentials"],
  "scopes_supported": ["openid", "fhirUser", "launch", "launch/patient",
                       "patient/*.rs", "user/*.rs", "system/*.rs"]
}

The capabilities array tells you exactly which SMART features this server supports. If launch-ehr appears, the server can initiate an EHR launch. If client-confidential-asymmetric appears, the server supports backend services using signed JWTs. Checking this document first prevents a category of integration errors where apps assume capabilities that the server does not advertise.

Flow 1: Patient Standalone Launch

The patient standalone launch is the most common flow for consumer-facing health apps -- think mobile apps that patients use to review their lab results, manage their medications, or share records with a new provider. The app opens outside the EHR entirely. The patient starts from their phone's home screen or a web browser and connects to their health system's FHIR server.

The term "standalone" means there is no pre-existing EHR session handing the app a context. The app must initiate everything from scratch and the patient must authenticate directly with their health system.

Sequence Diagram: Patient Standalone Launch
Patient App Authorization Server FHIR Server | | | |-- GET /.well-known/smart-configuration ------------->| |<-- { authorization_endpoint, token_endpoint } -------| | | | |-- Redirect to authorization_endpoint | | ?response_type=code | | &client_id=my-app | | &redirect_uri=https://myapp.com/callback | | &scope=launch/patient patient/*.rs openid fhirUser | | &state=random-state-value | | &code_challenge=S256-hash | | &code_challenge_method=S256 ------>| | | | | | [Patient logs in at health system portal] | | [Patient selects which data to share] | | [Patient grants consent] | | | | |<-- Redirect to redirect_uri | | ?code=AUTH_CODE&state=random-state-value | | | | |-- POST /token | | | grant_type=authorization_code | | code=AUTH_CODE | | redirect_uri=https://myapp.com/callback | | code_verifier=original-verifier ------>| | | | | |<-- { access_token, patient: "Patient/123", | | token_type: "Bearer", expires_in: 3600 } | | | | |-- GET /fhir/R4/Patient/123 ----------------------->| | Authorization: Bearer {access_token} | |<-- Patient resource (JSON) -------------------------|

Several elements in this diagram deserve attention. The scope=launch/patient value tells the authorization server that when the user logs in, it should present them with a patient picker interface so they can confirm which patient record the app should access. For a patient-facing app where the logged-in user is the patient, this is typically automatic. For a clinician standalone app, it prompts the clinician to select a patient.

The code_challenge and code_challenge_method=S256 parameters implement PKCE (Proof Key for Code Exchange, defined in RFC 7636). PKCE prevents an attacker who intercepts the authorization code from using it. The app generates a random code_verifier string, computes its SHA-256 hash (the code_challenge), and sends the hash with the initial request. At token exchange, it sends the original verifier. The server verifies that the hash matches, confirming the token request came from the same party that initiated the authorization request. PKCE is mandatory for public clients (native apps, single-page applications) in SMART App Launch v2.

The token response includes a patient field containing the FHIR resource ID of the patient who consented. The app uses this ID for all subsequent data requests, scoped to that patient's record only.

Flow 2: EHR Launch

The EHR launch happens when a clinician is already working inside an EHR and opens a SMART app from within that EHR session. A cardiologist viewing a patient's chart might click a button to open a risk-scoring app directly from the chart. The EHR already knows which patient is active, which encounter is open, and who the clinician is. Rather than making the user re-authenticate and re-select a patient, the EHR passes that context to the SMART app automatically.

Sequence Diagram: EHR Launch
EHR System SMART App Authorization Server FHIR Server | | | | |-- Open app's | | | | launch_uri | | | | ?iss=https://fhir.example.com | | | &launch=LAUNCH_TOKEN ------>| | | | | | | | |-- GET /.well-known/smart-configuration ------>| | |<-- { authorization_endpoint, token_endpoint } | | | | | | |-- Redirect to authorization_endpoint | | | ?response_type=code | | | &client_id=risk-app | | | &redirect_uri=https://riskapp.com/callback | | | &scope=launch openid fhirUser patient/*.rs | | | &launch=LAUNCH_TOKEN | | | | &aud=https://fhir.example.com | | | &code_challenge=S256-hash ------->| | | | | | | [EHR confirms clinician identity; no re-login needed] | | [Patient context inherited from EHR session] | | | | | | |<-- Redirect to redirect_uri | | | ?code=AUTH_CODE | | | | | | | |-- POST /token | | | | grant_type=authorization_code | | | code=AUTH_CODE | | | code_verifier=original-verifier ------>| | | | | | | |<-- { access_token, patient: "Patient/456", | | | encounter: "Encounter/789", | | | fhirUser: "Practitioner/001" } | | | | | | |-- GET /fhir/R4/Observation?patient=456 ------>| | | Authorization: Bearer {access_token} | | |<-- Observation bundle (JSON) ----------------|

The critical difference from a standalone launch is the launch parameter. The EHR generates an opaque context token (the LAUNCH_TOKEN) when it opens the app's registered launch URL. This token encodes the current session state -- the patient, the encounter, the user -- on the EHR's side. The SMART app echoes this token back in the authorization request. When the authorization server receives it, it resolves the context and includes the patient ID, encounter ID, and practitioner identity in the token response.

Because the clinician is already authenticated in the EHR, they typically do not see a separate login screen. The EHR handles identity confirmation internally and passes the authorization code back to the app. From the clinician's perspective, the app simply opens within the EHR interface with the correct patient's data already loaded. The token response also carries fhirUser, identifying the practitioner as a FHIR Practitioner resource, which the app can use for audit logging or role-based UI decisions.

Flow 3: Backend Services

The backend services flow addresses a fundamentally different scenario: no human is present. A population health pipeline needs to query all diabetic patients in a health system for a quality reporting run. A care management platform needs to pull overnight ADT (Admit, Discharge, Transfer) notifications to update patient rosters. These are system-to-system operations running on a schedule or in response to events, with no user to authenticate and no browser to redirect.

Backend services use the OAuth 2.0 client_credentials grant, but with an important healthcare-specific modification: instead of a shared client secret, the client proves its identity using an asymmetric key pair. The client signs a JWT with its private key, the authorization server verifies it using the corresponding public key (which was registered with the server in advance), and if valid, returns an access token. No browser. No user. No redirect.

Sequence Diagram: Backend Services
Backend Service Authorization Server FHIR Server | | | |-- GET /.well-known/smart-configuration ---------------->| |<-- { token_endpoint, token_endpoint_auth_methods: ["private_key_jwt"] } | | | | [Build client_assertion JWT] | | | Header: { alg: "RS384", kid: "my-key-id" } | | Payload: { | | | iss: "my-backend-client-id", | | sub: "my-backend-client-id", | | aud: "https://fhir.example.com/oauth/token", | | jti: "unique-nonce-value", | | iat: 1761609600, | | | exp: 1761609900 | | | } | | | [Sign with RSA private key] | | | | | |-- POST /oauth/token | | | grant_type=client_credentials | | scope=system/Patient.read system/Observation.read | | client_assertion_type=urn:ietf:params:oauth: | | client-assertion-type:jwt-bearer | | client_assertion=eyJhbGci... ------>| | | | | | [Server verifies JWT signature | | using registered public key] | | [Server checks jti is not replayed] | | [Server checks exp is not past] | | | | |<-- { access_token, token_type: "Bearer", | | expires_in: 300, scope: "system/Patient.read system/Observation.read" } | | | |-- GET /fhir/R4/Patient?_count=100 ---------------------->| | Authorization: Bearer {access_token} | |<-- Patient bundle (all patients within authorized scope) |

The jti (JWT ID) claim in the client assertion is a replay attack prevention mechanism. Each JWT assertion must carry a unique identifier, and the authorization server must reject any assertion whose jti has already been used. This prevents an attacker who intercepts a signed JWT from reusing it after the legitimate request has completed. The specification requires that assertions expire within five minutes of their iat (issued-at) timestamp, limiting the window during which a stolen assertion could be replayed.

The public key must be registered with the authorization server before the backend service can authenticate. The SMART specification supports two registration approaches: a static JWKS (JSON Web Key Set) document uploaded during client registration, or a resolvable JWKS URL that the authorization server fetches dynamically. The URL-based approach is preferable in production because it allows key rotation without re-registering the client.

Understanding SMART Scopes

SMART scopes are the mechanism by which an app declares what data it needs access to. The scope syntax in SMART App Launch v2 follows a predictable pattern:

[context]/[ResourceType].[permissions]

The context prefix determines who the access applies to. The resource type is any FHIR resource type (or * as a wildcard). The permissions suffix uses a compact notation: c for create, r for read, u for update, d for delete, s for search. These can be combined, so .rs means read and search.

Scope Context What it grants Typical use
patient/Patient.rs patient Read and search Patient resources for the authorized patient only Patient-facing app reading the user's own demographics
patient/*.rs patient Read and search all resource types for the authorized patient Patient app accessing a full health summary
user/Observation.rs user Read and search Observation resources for patients the logged-in clinician has access to Clinician app reviewing lab results across their panel
system/Patient.read system Read all Patient resources across the server, regardless of user context Backend population health pipeline
system/*.read system Read all resource types across the server Backend bulk data export for analytics
launch/patient launch Requests that the EHR provide a patient context (either via picker or inherited session) Any app needing to scope data to a single patient

The scope context prefix is not a cosmetic distinction. A server that receives a token containing patient/Observation.rs is contractually obligated to enforce that the token can only access Observation resources belonging to the specific patient encoded in the token's patient claim. A user/ scope enforces the clinician's existing access control rules as defined in the EHR. A system/ scope operates independently of any user session and typically requires pre-authorization by a system administrator, not end-user consent. Using the wrong scope prefix -- particularly requesting system/ scopes from a user-facing app -- will be rejected by compliant authorization servers, and for good reason.

SMART v1 used broad scopes like patient/*.read. SMART v2 encourages granular scopes like patient/Observation.rs to align with HIPAA's minimum-necessary principle. Many EHR vendors still support the v1 syntax for backward compatibility, but new applications should request only the specific resource types and operations they actually need.

A Working Token Request Example

The public HAPI FHIR test server at hapi.fhir.org/baseR4 is an openly accessible sandbox for basic FHIR API testing and does not enforce SMART authorization out of the box. However, the token request format shown below is exactly what you would send against any SMART-compliant authorization server. Organizations building against a production server -- such as a health system running Smile CDR, Microsoft Azure Health Data Services, or Google Cloud Healthcare API -- can use this same pattern against those environments with valid credentials.

The following curl example demonstrates a backend services token request. Before running it, you need two things: a registered client ID and a private RSA key whose corresponding public key has been registered with the target authorization server.

Step 1: Discover the token endpoint.

curl -s https://fhir.example.com/baseR4/.well-known/smart-configuration \
  | python3 -m json.tool

Note the value of token_endpoint from the response. You will use it in step 3.

Step 2: Build and sign the client assertion JWT.

Most production implementations use a JWT library in their language of choice. The following Python snippet illustrates the payload construction:

import uuid, time, jwt  # pip install PyJWT cryptography

private_key = open("private_key.pem").read()

payload = {
    "iss": "my-backend-client-id",    # your registered client_id
    "sub": "my-backend-client-id",    # must match iss for backend services
    "aud": "https://fhir.example.com/oauth/token",  # token endpoint
    "jti": str(uuid.uuid4()),          # unique per request; never reuse
    "iat": int(time.time()),
    "exp": int(time.time()) + 300      # 5 minutes max
}

token = jwt.encode(
    payload,
    private_key,
    algorithm="RS384",
    headers={"kid": "my-key-id"}      # must match the kid in your registered JWKS
)
print(token)

Step 3: Exchange the signed JWT for an access token.

curl -X POST https://fhir.example.com/oauth/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data-urlencode "grant_type=client_credentials" \
  --data-urlencode "scope=system/Patient.read system/Observation.read" \
  --data-urlencode "client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer" \
  --data-urlencode "client_assertion=eyJhbGciOiJSUzM4NCIsImtpZCI6..."

A successful response returns an access token valid for the duration specified in expires_in (typically 300 seconds for backend service tokens):

{
  "access_token": "eyJhbGciOiJSUzI1NiIs...",
  "token_type": "Bearer",
  "expires_in": 300,
  "scope": "system/Patient.read system/Observation.read"
}

Step 4: Use the token to query the FHIR server.

curl https://fhir.example.com/baseR4/Patient?_count=10 \
  -H "Authorization: Bearer eyJhbGciOiJSUzI1NiIs..."

The FHIR server validates the bearer token against the authorization server (either introspecting it directly or verifying a signed JWT), confirms that the requested resource type and operation fall within the token's approved scopes, and returns the Patient bundle.

What Works Well and Where Friction Remains

SMART on FHIR has delivered genuine progress on healthcare interoperability. The standardization of launch flows means that a SMART-compliant app developed against one EHR can, in principle, be connected to any other SMART-compliant EHR without rebuilding the authentication layer. The ONC certification requirements have driven major EHR vendors -- Epic, Cerner (Oracle Health), Meditech, and others -- to implement conformant endpoints, creating a real ecosystem of portable healthcare applications. The CMS Patient Access API mandates, which require payers to expose FHIR R4 APIs secured with SMART, have extended this ecosystem to the insurance industry.

The friction points are worth naming honestly. First, "SMART-compliant" in practice varies. The specification defines a large capability set, and individual server implementations support different subsets. An app that works against Epic's SMART implementation may encounter scope naming differences, token lifetimes, or registration requirements that differ from a Cerner environment. The .well-known/smart-configuration discovery document helps, but it does not eliminate the need for environment-specific testing.

Second, app registration is still a manual, offline process at most health systems. Before your app can initiate any SMART flow, a health system's IT and security team must review and approve it, assign a client ID, and register your redirect URIs and public keys. This process can take weeks to months at large institutions, which creates a meaningful barrier for startups and smaller development teams. No part of SMART automates this approval process.

Third, the backend services flow requires asymmetric key management discipline. Rotating keys, ensuring the JWKS URL remains accessible, and handling key expiration without breaking production pipelines demands operational maturity that many healthcare IT teams are still developing. A backend service whose JWKS URL becomes unreachable will fail silently at token request time, and debugging that failure in a production pipeline is non-trivial.

Fourth, SMART on FHIR secures the transport and authorization layer, but it does not guarantee data quality or completeness. A valid access token against a compliant FHIR endpoint still returns whatever data the health system has actually entered into its EHR. Gaps, inconsistencies, and variations in clinical documentation practices all pass through SMART authorization unchanged.

Choosing the Right Flow for Your Use Case

The three flows are not interchangeable. Selecting the wrong one either creates unnecessary user friction or introduces authorization scope that exceeds what the use case warrants.

Use the patient standalone launch when you are building a consumer-facing application that patients use independently, outside any EHR session. The patient authenticates through their health system's patient portal and explicitly consents to what data the app can access. This flow is appropriate for personal health record apps, chronic disease management tools, and any application where the patient is the primary user and the data subject.

Use the EHR launch when you are building a clinical tool designed to be used by clinicians within the EHR workflow. The app opens in the context of a patient chart, inherits the session, and does not interrupt the clinician with a separate login. This flow is appropriate for clinical decision support tools, specialty documentation apps, and any application where seamless integration with the EHR workflow is more important than standalone portability.

Use the backend services flow when no human user is present. Population health analytics, care gap identification pipelines, bulk data exports for quality reporting, and system-to-system data synchronization all fall into this category. The backend services flow carries the highest level of access -- system/ scopes can access data across the entire patient population -- and accordingly requires the most rigorous pre-authorization and organizational approval before a server will issue tokens against it.

SMART on FHIR is, ultimately, a sensible application of standard security protocols to a domain that needed them badly. Healthcare data has historically been siloed not because of malice but because there was no agreed-upon, secure mechanism for sharing it across systems and organizations. SMART provides that mechanism. Understanding its three launch flows, its scope vocabulary, and its token request patterns is increasingly a prerequisite for anyone building or integrating healthcare applications in a regulatory environment where interoperability is now a legal requirement rather than an aspiration.
