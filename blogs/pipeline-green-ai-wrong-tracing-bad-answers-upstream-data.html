Your Pipeline Is Green but Your AI Is Wrong: Tracing Bad Answers Back to Upstream Data

A green pipeline status and a healthy model endpoint do not guarantee correct answers. This post walks through a real failure pattern where a silent schema change upstream corrupts retrieval quality, and shows how connecting data lineage to distributed traces resolves root cause in minutes rather than days.

Published: November 16, 2026

Every production AI system built on a retrieval-augmented generation (RAG) architecture rests on a supply chain of data transformations that most engineering teams treat as invisible once deployed. The orchestration job is green. The embedding pipeline completed without errors. The vector database index refreshed on schedule. Yet users are receiving answers that are factually stale, contextually incomplete, or quietly wrong in ways that never trigger an alert. This is not a hypothetical edge case; it is the dominant failure mode observed across enterprise AI deployments as organizations scale from prototype to production.

The core problem is architectural: data pipeline observability and AI model observability have historically lived in entirely separate toolchains. Data engineers monitor Airflow DAG status, dbt run results, and row-count anomaly detectors. AI engineers monitor prompt token counts, model latency, and LLM-as-a-judge evaluation scores. Neither discipline, operating in isolation, possesses the instrumentation necessary to connect a degraded language model response to the upstream data transformation that caused it. This post demonstrates how that gap is closed, through a concrete failure walkthrough and a step-by-step instrumentation architecture using OpenLineage, OpenTelemetry GenAI semantic conventions, and MLflow 3.

The Failure Nobody Sees Coming

Consider a production internal knowledge assistant deployed at a mid-sized financial services organization. The system answers employee questions about regulatory policy documents, product specifications, and compliance procedures. Its architecture is representative: a dbt pipeline transforms raw policy documents from a source database into a cleaned policy_chunks table in a Snowflake data warehouse; a nightly embedding job reads from that table, generates text embeddings using an embedding model API, and upserts the resulting vectors into a Pinecone index; a FastAPI application wraps a retrieval step against that index followed by a generation step using a hosted large language model.

Three weeks after a routine quarterly schema migration, the system begins producing answers that reference outdated policy versions and omit critical compliance caveats that the organization's legal team had explicitly added. No alert fires. The pipeline DAG shows all green. The model endpoint returns HTTP 200 on every request. The P99 latency is within normal bounds. A user submits a complaint through a Slack channel. The investigation begins.

What Actually Happened: The Silent Column Drop

The quarterly schema migration included a dbt model refactor that renamed the policy_summary_text column to document_excerpt across three upstream models. The engineer who made the change updated the final mart model correctly, but one intermediate staging model still referenced the old column name via a SELECT *. Because dbt resolved the ambiguity by returning a NULL value rather than raising a compile error in that specific materialization path, the downstream policy_chunks table began populating the text field used for embedding generation with None values, silently substituted as the string "None" by the Python ingestion script's f-string formatting.

The resulting text chunks embedded into Pinecone looked like this:

# Before the schema migration (healthy chunk)
"Section 4.2 - Anti-Money Laundering Requirements: Transactions exceeding $10,000 must
 be reported within 15 business days. Customer identification verification is mandatory
 for all wire transfers above $3,000. Updated: Q3 2026."

# After the silent column drop (corrupted chunk)
"None"

The embedding model faithfully embedded the string "None" as a valid vector. The Pinecone index accepted the upsert without error. The similarity search returned those vectors as top-k results for queries semantically related to null-like or absent content. The LLM received impoverished context and synthesized plausible-sounding but factually unsupported answers. The pipeline remained entirely green throughout.

The monitoring gap: Standard pipeline health checks verify job completion status and row counts. They do not verify the semantic integrity of the content written to the vector index. Standard LLM monitoring verifies response latency and token usage. It does not verify that retrieved context is substantive. The failure lived between both systems, invisible to each.

The Architecture of Connected Observability

Closing this monitoring gap requires treating the data supply chain and the AI inference chain as a single instrumented system rather than two adjacent systems that happen to exchange data. Three telemetry layers must be present and connected for end-to-end root cause analysis to be possible within minutes.

The three-layer observability architecture. Data pipeline events flow into an OpenLineage store; inference traces flow into MLflow 3. The root cause analysis layer joins them via shared chunk provenance metadata attached at embedding time.

Layer 1: Data Pipeline Lineage with OpenLineage

OpenLineage, the open standard for data lineage collection maintained by the Linux Foundation, defines a structured event format that any data pipeline tool can emit when it reads or writes a dataset. dbt, Apache Spark, Apache Airflow, Flink, and several commercial warehouses support native OpenLineage integration. Each event carries a schemaDatasetFacet describing the columns present in the dataset at the time of the job run. When a column is dropped, the next OpenLineage event for that dataset will reflect a narrower schema, creating a versioned record of the structural change that any downstream consumer can query.

Configuring dbt to emit OpenLineage events requires installing the openlineage-dbt package and pointing the OpenLineage client at a Marquez server (or any OpenLineage-compatible backend) via environment variables, as there is no dedicated OpenLineage block inside dbt's own profiles.yml. Critically, dbt must also be invoked through the dbt-ol wrapper rather than the plain dbt command, or no events will be emitted at all, regardless of configuration: 

# Environment variables read by the OpenLineage Python client
export OPENLINEAGE_URL=http://localhost:5000
export OPENLINEAGE_NAMESPACE="finance_policy_rag"
# Optional: export OPENLINEAGE_API_KEY=... if your backend requires bearer auth

# Run dbt through the OpenLineage wrapper, not `dbt run`, so events are emitted
dbt-ol run

For more complex transport configuration (custom headers, a non-default endpoint path), use a separate openlineage.yml file referenced via the OPENLINEAGE_CONFIG environment variable, rather than embedding it in profiles.yml:

# openlineage.yml
transport:
  type: http
  url: http://localhost:5000
  endpoint: /api/v1/lineage

export OPENLINEAGE_CONFIG=/path/to/openlineage.yml
dbt-ol run

With this configuration active, every dbt-ol run invocation emits a structured JSON event to Marquez. The event for the schema migration run that introduced the silent column drop would include a schemaDatasetFacet that no longer lists policy_summary_text. A lineage monitoring alert configured against that dataset would detect the schema contraction and fire before the embedding pipeline processes the corrupted table: 

# Example: query Marquez API for schema changes on a specific dataset
import requests

MARQUEZ_URL = "http://localhost:5000"
NAMESPACE = "finance_policy_rag"
DATASET = "policy_chunks"

response = requests.get(
    f"{MARQUEZ_URL}/api/v1/namespaces/{NAMESPACE}/datasets/{DATASET}/versions",
    params={"limit": 5}
)
versions = response.json()["versions"]

# Compare the two most recent schema versions
prev_cols = {f["name"] for f in versions[1]["facets"]["schema"]["fields"]}
curr_cols = {f["name"] for f in versions[0]["facets"]["schema"]["fields"]}

dropped = prev_cols - curr_cols
added   = curr_cols - prev_cols

if dropped:
    print(f"ALERT: Columns dropped from {DATASET}: {dropped}")
    # Fire PagerDuty / Slack notification here
if added:
    print(f"INFO: New columns added to {DATASET}: {added}")

This alert, had it been in place, would have flagged the column drop within minutes of the dbt run completing, before the embedding pipeline consumed the corrupted table. The pipeline would still have shown green, but the lineage monitor would have surfaced the semantic change that the job status alone cannot reveal.

Layer 2: Chunk-Level Provenance Tags at Embedding Time

The bridge between the data pipeline layer and the inference layer is the provenance metadata attached to each vector during the embedding ingestion job. Table-level lineage is insufficient for root cause analysis of RAG failures, because a single Pinecone query may return vectors originating from multiple dbt models, ingestion batches, and time windows. The investigation must be traceable to the specific chunk that caused the retrieval failure.

The embedding ingestion job should attach structured metadata to every vector upserted into the index. At minimum, this metadata should include the source table name, the dbt model version or run ID, the ingestion batch timestamp, and a hash of the chunk content. The following example demonstrates this pattern using the current (v3+) Pinecone Python SDK, which requires constructing a Pinecone client instance rather than calling module-level functions:

import hashlib
import os
from pinecone import Pinecone
from datetime import datetime, timezone

pc = Pinecone(api_key=os.environ["PINECONE_API_KEY"])
pinecone_index = pc.Index("policy-knowledge-base")

def embed_and_upsert(chunks: list[dict], dbt_run_id: str, source_table: str):
    """
    Embed text chunks and upsert into Pinecone with full provenance metadata.
    Each vector carries the metadata needed to trace it back to its upstream source.
    """
    batch_ts = datetime.now(timezone.utc).isoformat()
    vectors = []

    for chunk in chunks:
        text = chunk.get("policy_summary_text") or chunk.get("document_excerpt", "")

        # Fail loudly rather than embed empty or null content
        if not text or text.strip().lower() in ("none", "null", ""):
            raise ValueError(
                f"Empty or null text content for chunk id={chunk['id']}. "
                f"Possible upstream column drop in {source_table}. "
                f"dbt_run_id={dbt_run_id}"
            )

        embedding = get_embedding(text)  # your embedding API call
        content_hash = hashlib.sha256(text.encode()).hexdigest()[:16]

        vectors.append({
            "id": chunk["id"],
            "values": embedding,
            "metadata": {
                "source_table": source_table,
                "dbt_run_id": dbt_run_id,
                "ingestion_batch_ts": batch_ts,
                "content_hash": content_hash,
                "text_length": len(text),
            }
        })

    pinecone_index.upsert(vectors=vectors)
    return len(vectors)

The explicit validation transforms the silent failure into a loud one: instead of embedding the string "None" and continuing, the job raises a ValueError with a message that names the source table and the dbt run ID. The embedding pipeline fails visibly, and the alert paths that engineers have configured for job failures are triggered. The pipeline is no longer green, and the error message contains the exact information needed to begin the investigation.

Layer 3: LLM Tracing with OpenTelemetry GenAI Semantic Conventions

The inference layer must emit structured trace spans that capture the retrieved context with its provenance metadata attached. OpenTelemetry's GenAI semantic conventions define a working attribute vocabulary for spans covering embedding generation, vector retrieval, and language model generation; attributes like gen_ai.request.model, gen_ai.usage.input_tokens, and gen_ai.usage.output_tokens are already widely implemented across instrumentation libraries. It's worth being precise about their status, though: as of this writing, every gen_ai.* attribute remains at "Development" stability in OpenTelemetry's own registry; none has reached "Stable." If anything, the ecosystem moved toward more flux in 2026, not less: in June 2026, the GenAI conventions were split out of OpenTelemetry's core semantic-conventions repository into a dedicated semantic-conventions-genai repo specifically so this area could keep iterating without being held to the main spec's stability bar. MLflow 3, which reached general availability in June 2025, provides a practical, OTel-compatible tracing implementation that teams can build on today with the understanding that upstream attribute names may still shift.

The following example instruments a FastAPI RAG endpoint using MLflow 3's tracing decorator, capturing both the retrieval span and the generation span with provenance data propagated from the retrieved vector metadata:

import os
import mlflow
from mlflow.entities import SpanEvent
from pinecone import Pinecone

mlflow.set_tracking_uri("http://localhost:5001")
mlflow.set_experiment("policy-assistant-production")

pc = Pinecone(api_key=os.environ["PINECONE_API_KEY"])

@mlflow.trace
def retrieve_and_generate(query: str) -> dict:
    """
    Full RAG inference function with MLflow 3 tracing.
    The @mlflow.trace decorator creates a root span; child spans are added manually.
    """
    with mlflow.start_span(name="vector_retrieval") as retrieval_span:
        index = pc.Index("policy-knowledge-base")
        query_embedding = get_embedding(query)
        results = index.query(
            vector=query_embedding,
            top_k=5,
            include_metadata=True
        )
        # Attach provenance of every retrieved chunk to the span
        retrieved_chunks = []
        for match in results["matches"]:
            chunk_info = {
                "score": match["score"],
                "source_table": match["metadata"].get("source_table"),
                "dbt_run_id":   match["metadata"].get("dbt_run_id"),
                "ingestion_ts": match["metadata"].get("ingestion_batch_ts"),
                "content_hash": match["metadata"].get("content_hash"),
                "text_length":  match["metadata"].get("text_length"),
            }
            retrieved_chunks.append(chunk_info)

        retrieval_span.set_attributes({
            "gen_ai.retrieval.top_k": 5,
            "gen_ai.retrieval.results_count": len(results["matches"]),
        })
        # Log chunk provenance as a span event (not a high-cardinality attribute)
        retrieval_span.add_event(
            SpanEvent(
                name="retrieved_chunks_provenance",
                attributes={"chunks": str(retrieved_chunks)},
            )
        )

    with mlflow.start_span(name="llm_generation") as gen_span:
        context = "\n\n".join(
            m["metadata"].get("text", "") for m in results["matches"]
        )
        prompt = build_prompt(query, context)
        response = call_llm(prompt)

        gen_span.set_attributes({
            "gen_ai.request.model": "gpt-4o",
            "gen_ai.usage.input_tokens": response["usage"]["prompt_tokens"],
            "gen_ai.usage.output_tokens": response["usage"]["completion_tokens"],
        })

    return {
        "answer": response["choices"][0]["message"]["content"],
        "retrieved_chunks": retrieved_chunks,
    }

With this instrumentation active, every inference request produces an MLflow 3 trace that contains the exact dbt run ID and source table for every chunk that contributed to the answer. When a user flags an incorrect response, the investigation path becomes deterministic.

The Root Cause Investigation: From Bad Answer to Broken Transform in Minutes

With the three observability layers in place, the investigation workflow that would have taken days in the original scenario is reduced to a structured sequence of queries. The following walkthrough traces the investigation path from a user-flagged bad answer back to the dbt model that introduced the column drop.

Step 1: Locate the Flagged Trace in MLflow 3

The user submits a thumbs-down rating on the assistant response. That rating is linked to the MLflow 3 trace ID that was returned in the response HTTP header. The engineer opens the MLflow 3 trace UI, navigates to the flagged trace, and expands the vector_retrieval span. The retrieved_chunks_provenance event shows five chunks, all with text_length: 4 (the length of the string "None") and a shared dbt_run_id: run_20261103_142301.

Step 2: Query OpenLineage for the dbt Run

The engineer queries the Marquez API for the lineage event associated with run_20261103_142301. The event record shows that the run wrote to the policy_chunks dataset and that the output schemaDatasetFacet no longer includes the policy_summary_text field. The event also shows the upstream input datasets: stg_policy_documents and stg_compliance_caveats. The column was present in the input schema but absent from the output schema, confirming that the transformation logic is responsible.

Step 3: Examine the dbt Model DAG

Using the dbt Cloud IDE or the dbt docs lineage graph, the engineer navigates to the policy_chunks mart model and traces the policy_summary_text field through its upstream staging models. The intermediate model stg_policy_documents shows the field resolved as NULL because the SELECT * propagation missed the column rename in the policy_summary_text to document_excerpt migration. The specific dbt model, the specific commit, and the specific column are all identified.

Step 4: Scope the Impact and Remediate

The engineer queries the Pinecone index for all vectors whose metadata contains dbt_run_id: run_20261103_142301 and verifies the text_length: 4 pattern to confirm the full set of corrupted chunks. The dbt model fix is applied, the corrected run executes, and the embedding pipeline re-ingests only the affected chunk IDs using the ingestion timestamp range from the lineage event. Total investigation time: approximately 18 minutes. Without the connected observability stack, the same investigation averaged 3.5 days in the organization's pre-instrumentation incident retrospectives.

Canary Queries: Detecting Degradation Before Users Notice

Reactive investigation after a user complaint is a minimum viable capability. A more mature posture adds proactive detection through canary evaluation queries that run on a regular schedule against the production inference stack. The concept is straightforward: maintain a curated set of queries for which the correct answers are known and stable, run them against the system at scheduled intervals, score the responses using a deterministic similarity metric or an LLM-as-a-judge scorer, and alert when the aggregate score drops below a configured threshold.

import mlflow

CANARY_QUERIES = [
    {
        "query": "What is the reporting deadline for transactions exceeding $10,000?",
        "expected_keywords": ["15 business days", "15-day", "BSA", "Bank Secrecy Act"],
        "min_keyword_hits": 2,
    },
    {
        "query": "What documentation is required for wire transfers above $3,000?",
        "expected_keywords": ["customer identification", "CIP", "identity verification"],
        "min_keyword_hits": 1,
    },
]

def run_canary_evaluation():
    with mlflow.start_run(run_name="canary_eval"):
        pass_count = 0
        for item in CANARY_QUERIES:
            result = retrieve_and_generate(item["query"])
            answer = result["answer"].lower()
            hits = sum(1 for kw in item["expected_keywords"] if kw.lower() in answer)
            passed = hits >= item["min_keyword_hits"]
            if passed:
                pass_count += 1
            mlflow.log_metric(f"canary_pass_{item['query'][:30]}", int(passed))

        overall_pass_rate = pass_count / len(CANARY_QUERIES)
        mlflow.log_metric("canary_pass_rate", overall_pass_rate)

        if overall_pass_rate < 0.80:
            # Trigger alerting webhook
            raise RuntimeError(
                f"Canary evaluation failed: pass_rate={overall_pass_rate:.2%}. "
                "Possible upstream data quality regression."
            )

Scheduled as a daily Airflow task, this evaluation would have detected the "None" embedding corruption within 24 hours of the dbt run, long before the user complaint arrived. The alert message explicitly attributes the failure to a possible upstream data quality regression rather than a model failure, directing the investigation toward the data pipeline layer from the first notification.

What OpenTelemetry's GenAI Conventions Standardize and What They Do Not

It's worth restating precisely where the OpenTelemetry GenAI semantic conventions stand, since the status matters for how much teams should rely on attribute names staying put. As of this writing, no gen_ai.* attribute, span, or metric has reached "Stable" in OpenTelemetry's own registry; the entire namespace sits at "Development," the first rung of OTel's stability ladder, and the June 2026 move into a separate semantic-conventions-genai repository was explicitly meant to let the area iterate faster than the core stability process allows. Attributes like gen_ai.request.model, gen_ai.usage.input_tokens, and gen_ai.usage.output_tokens are nonetheless widely implemented and reasonably consistent across compatible instrumentation libraries for frameworks including LangChain, LlamaIndex, and vLLM, which meaningfully reduces instrumentation overhead in practice even without a formal stability guarantee.

Retrieval-layer attributes are further behind than the core token-usage ones. Attributes such as gen_ai.retrieval.top_k and gen_ai.data_source.id appear in vendor implementations but lack even the loose cross-framework consistency that the core LLM-call attributes have achieved. This means teams must define and maintain their own attribute naming convention for chunk provenance metadata, which introduces a schema drift risk within the trace data itself. Early-adopting instrumentation packages have been known to rename attributes during minor version bumps without issuing migration guidance, leaving teams to manage attribute renaming manually in OTel Collector transform processors.

Practical mitigation: Define a canonical internal attribute vocabulary for retrieval provenance metadata and enforce it in an OTel Collector transform processor. This decouples your storage backend and dashboards from the volatility of upstream instrumentation library releases. The transform processor configuration shown below normalizes two common attribute naming variants into a single canonical form:

# otel-collector-config.yaml
processors:
  transform:
    error_mode: ignore
    trace_statements:
      - context: span
        statements:
          # Normalize retrieval model attribute name variants
          - set(attributes["gen_ai.request.model"], attributes["llm.model_name"])
            where attributes["llm.model_name"] != nil
          # Normalize chunk source table attribute
          - set(attributes["rag.chunk.source_table"], attributes["retrieval.source"])
            where attributes["retrieval.source"] != nil

The Organizational Dimension: Who Owns the Bridge

The technical instrumentation described in this post solves a tractable engineering problem. The harder problem is organizational. Data pipeline observability is typically owned by a data engineering or data platform team, while AI model observability is owned by an ML engineering or AI product team. Neither team has a natural incentive to build and maintain the bridge between their respective toolchains, because the failure mode it addresses is invisible when it occurs and attributed to the other team when it surfaces.

Organizations that have resolved this effectively treat the embedding ingestion pipeline as a seam that both teams co-own. The data engineering team owns the upstream schema contract and the OpenLineage instrumentation. The AI engineering team owns the chunk validation logic, the provenance metadata schema, and the canary evaluation framework. A shared on-call rotation for the embedding pipeline formalized as a service rather than a script creates the accountability structure that sustains the investment in connected observability over time.

The tooling ecosystem that supports this architecture has matured substantially since MLflow 3's release in mid-2025. MLflow 3's native integration with Databricks Unity Catalog allows trace data to be stored as Delta tables, enabling direct SQL queries over production inference history. OpenLineage's support across dbt, Spark, and Airflow means that lineage instrumentation is largely configuration and a changed run command (dbt-ol in place of dbt) rather than custom code. The remaining work is the deliberate act of connecting the two systems at the vector metadata layer, which requires no specialized tooling and no vendor lock-in: only the discipline to treat chunk provenance as a first-class data artifact rather than a debug afterthought.

Limitations and What This Approach Does Not Solve

Connected lineage and tracing is not a universal solution for AI answer quality problems. Several important failure modes remain outside its scope. Retrieval quality degradation caused by embedding model updates, where the same text produces a different vector because the embedding model changed versions, is not detectable through data lineage alone; it requires explicit versioning of the embedding model used at ingest time and re-embedding on model change. Answer quality problems caused by LLM model updates, reasoning failures, or instruction-following regressions are model-layer problems that require evaluation frameworks rather than data lineage. Schema change detection through OpenLineage is also limited to datasets for which lineage integration is configured; legacy systems emitting flat files or proprietary formats may not support OpenLineage emission without custom integration work.

Furthermore, connecting a bad answer to a specific upstream data defect requires that the answer actually be flagged as bad through some feedback mechanism. Teams without user feedback collection, automated evaluation guardrails, or canary monitoring will not receive the signal that initiates the investigation, regardless of how well the lineage and tracing instrumentation is configured. The observability architecture described here amplifies and accelerates the investigation once a defect signal exists; it does not substitute for the defect detection capability that must precede it.

Taken together, however, lineage-connected tracing represents the most direct path from the experience that most AI platform teams are living today (separate dashboards, separate on-call, and no way to explain a bad answer without a multi-day investigation) to an operational posture where the data supply chain is as observable as the model it feeds. The engineering investment is modest relative to the reduction in mean time to resolution it delivers, and the organizational discipline it requires is the same discipline that distinguishes mature data platforms from fragile ones.
