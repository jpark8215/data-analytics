When a Pipeline Fails at 3am: Building a Power Automate Flow Where AI Analyzes the Error and Decides What Happens Next

A step-by-step guide to building a Power Automate cloud flow that catches ADF or Fabric pipeline failures, classifies them with an AI prompt action, and routes each case automatically: silent retry, Teams approval request, or on-call page, with everything logged for a Power BI measurement report.

Published: November 18, 2026

The email arrives at 3:17 in the morning. Subject line: Pipeline 'sales_mart_refresh' Failed [ADF-PROD]. The body contains a stack trace, an activity run ID, and a timestamp. For the engineer whose phone just vibrated, the next thirty minutes follow a predictable and exhausting script: open the Azure portal, navigate to the Data Factory monitoring view, expand the failed activity, read the error message, assess whether it is the kind of failure that resolves on a retry or the kind that requires investigation, and then decide whether to wake anyone else up. Most of the time, the error is a transient network timeout that would have resolved itself if the pipeline had simply tried again. The engineer retries manually, the pipeline succeeds, and two hours of sleep are lost to a problem that never required human judgment at all.

This post builds a Power Automate cloud flow that eliminates the routine triage step by inserting an AI analysis action between the failure alert and the human response. The AI reads the error context, categorizes the failure, assigns a severity, and proposes an action. The flow then routes accordingly: transient failures are retried silently and logged; medium-severity failures are summarized in a Teams message where an approver can confirm before any fix runs; high-severity failures or cases where the AI returns low confidence go directly to the on-call engineer with the full analysis attached. At no point does the AI trigger a destructive operation on its own.

Choosing the Right Build Path in 2026

Power Automate in 2026 offers three distinct paths for embedding AI reasoning into automation workflows, and choosing the wrong one for the wrong use case is a common source of both over-engineering and unexpected cost.

Path What It Is Best For Cost Model
AI actions in cloud flows The "Run a Prompt" AI Builder action embedded directly in a standard cloud flow Deterministic routing with one AI step; predictable behavior; standard Power Automate licensing AI Builder credits per prompt run; the rest of the flow uses standard Power Automate execution limits
Agent flows in Copilot Studio Flows managed and triggered by a Copilot Studio agent that calls them as tools mid-conversation Multi-turn reasoning; dynamic tool selection; when the agent must decide which flow to invoke based on context Copilot Credits: 13 credits per 100 flow actions, plus 5 credits per agent action invocation, per Microsoft's 2026 pricing documentation
Autonomous Copilot Studio agents Agents with memory and planning that trigger flows as background tools without a human in the conversation Complex, multi-step incident response involving multiple systems and unbounded reasoning chains Highest: autonomous trigger credits plus agent action credits per execution; plan carefully against tenant capacity pool

This post uses the first path: AI actions inside a standard cloud flow. The reasoning is deliberate. Pipeline failure triage follows a finite decision tree that is fully expressible in a cloud flow's switch-and-branch structure. The AI is responsible for one classification step, not for orchestrating the entire response. That separation makes the flow's behavior auditable, its cost predictable, and its guardrails enforceable without depending on an agent's reasoning chain staying within expected bounds. The appropriate time to graduate to agent flows is when the response requires dynamic tool selection across multiple systems, such as when the correct remediation action differs substantially across pipeline types and the agent must consult a knowledge base, run a diagnostic query, and choose from a library of fix procedures. For a nightly ETL monitoring flow, cloud flow routing with one AI step is both sufficient and preferable.

The Flow Architecture

The complete flow has eight logical stages. The diagram below shows the structure before the step-by-step build begins.

The complete Power Automate flow. The AI analysis stage produces a structured JSON response; the Switch action branches on the category field. All three paths converge at the Dataverse log step.

Step 1: Trigger and Collect Context

Azure Data Factory and Microsoft Fabric Data Factory both support alert rules that send email notifications when a pipeline run fails. The standard alert email contains the pipeline name, the activity that failed, the error message, and a link to the monitoring view. Power Automate's When a new email arrives (V3) trigger, filtered to the ADF alert sender address and a subject containing the word "Failed," catches these reliably.

Once triggered, the flow needs four pieces of context before it can call the AI action:

  • Pipeline name: extractable from the email subject using a split() expression on the subject line pattern Pipeline 'X' Failed
  • Error message: extractable from the email body using a Compose action with a substring() expression targeting the error block
  • Recent run history: an HTTP action calling the ADF REST API's "Pipeline Runs - Query By Factory" endpoint, filtered to the last 48 hours for the matching pipeline name. This is a POST request with the time window passed in the JSON body, not a GET with query parameters, as the ADF Pipeline Runs API doesn't support filtering via query string
  • Affected table or dataset: either parsed from the error body or pulled from a Dataverse table that maps pipeline names to their target datasets

For the ADF REST API call, the flow's connection should use a service principal with the Data Factory Contributor role scoped to the specific factory. This avoids granting broad subscription-level read permissions to the flow's identity. 

// Power Automate expression: extract pipeline name from subject
// Subject format: "Pipeline 'sales_mart_refresh' Failed [ADF-PROD]"

trim(
  split(
    split(triggerOutputs()?['body/subject'], '''')[1],
    ''''
  )[0]
)

The run-history lookup itself is a POST to the factory-level query endpoint, with the time window and an optional pipeline-name filter in the request body:

POST https://management.azure.com/subscriptions/{subscriptionId}/
  resourceGroups/{resourceGroupName}/providers/Microsoft.DataFactory/
  factories/{factoryName}/queryPipelineRuns
  ?api-version=2018-06-01

// Request body
{
  "lastUpdatedAfter": "@{addHours(utcNow(), -48)}",
  "lastUpdatedBefore": "@{utcNow()}",
  "filters": [
    {
      "operand": "PipelineName",
      "operator": "Equals",
      "values": ["@{variables('PipelineName')}"]
    }
  ]
}

Step 2: The AI Analysis Action and Prompt

The AI analysis step uses Power Automate's Run a Prompt action from the AI Builder connector. This action calls an AI Builder custom prompt that you define and store in your Power Platform environment. The prompt is the most important part of this flow: it determines the quality of the classification, the consistency of the JSON schema, and the reliability of every downstream routing decision.

Create the prompt in the AI Builder Hub before building the flow. Storing it as a managed resource rather than embedding it inline in the flow ensures that it survives environment migrations and can be updated without editing the flow itself. The following is the exact prompt text to use:

You are a data engineering operations assistant. Analyze the following Azure Data Factory or Microsoft Fabric pipeline failure and return a structured JSON classification. PIPELINE NAME: @{variables('PipelineName')} ERROR MESSAGE: @{variables('ErrorMessage')} RECENT RUN HISTORY (last 48h): @{variables('RunHistory')} AFFECTED TABLE: @{variables('AffectedTable')} Classify this failure and return ONLY valid JSON in the following exact schema. Do not include any text outside the JSON block. { "probable_cause": "One sentence describing the most likely root cause", "category": "TRANSIENT | SCHEMA_CHANGE | PERMISSIONS | DATA_ISSUE | UNKNOWN", "severity": "LOW | MEDIUM | HIGH", "confidence": 0.0, "recommended_action": "One sentence describing the recommended next step", "retry_safe": true } Category definitions: - TRANSIENT: network timeout, throttling, transient service unavailability, rate limit - SCHEMA_CHANGE: column missing, type mismatch, table not found, schema evolution error - PERMISSIONS: access denied, unauthorized, missing role assignment, credential expired - DATA_ISSUE: null constraint violation, referential integrity failure, bad source data - UNKNOWN: none of the above categories match with reasonable confidence Set confidence between 0.0 (no confidence) and 1.0 (certain). Set retry_safe to true only if retrying the pipeline immediately is unlikely to cause data duplication or corruption. Respond with JSON only.

Several design decisions in this prompt warrant explanation. The category field is constrained to a fixed enumeration. If the AI returns a value outside this list, the flow's subsequent Switch action will fall through to the default branch, which pages the on-call engineer. This is intentional: an unexpected category is treated as low-confidence and escalated to a human. The confidence field enables a second routing filter: even if the category is TRANSIENT, a confidence score below 0.75 triggers the Teams approval path rather than an automatic retry. The retry_safe field prevents the flow from auto-retrying a failure that could cause duplicate writes if the pipeline had already partially succeeded before failing.

After the Run a Prompt action, add a Parse JSON action targeting the prompt's text output. Set the schema to match the JSON structure above. This converts the AI's text response into typed properties that subsequent condition and switch actions can reference directly without additional string parsing.

AI Builder licensing note: The Run a Prompt action consumes AI Builder credits. Each prompt run is billed against the AI Builder credit allocation for the environment. Ensure that credits are explicitly allocated to your target environment in the Power Platform Admin Center under Resources > Capacity > AI Builder before deploying this flow to production. Credit depletion causes the action to return a 429 error, which the flow's error handler should catch and route to the on-call path as a fallback.

Step 3: Route by the AI's Decision

The routing logic uses a Switch action on the category parsed from the AI's JSON output, with an additional confidence check layered inside the TRANSIENT case.

Branch A: Transient Failure (Auto-Retry)

When the category is TRANSIENT, retry_safe is true, and confidence is at or above 0.75, the flow calls the ADF REST API to trigger a pipeline rerun. The API endpoint for this action is:

POST https://management.azure.com/subscriptions/{subscriptionId}/
  resourceGroups/{resourceGroupName}/providers/Microsoft.DataFactory/
  factories/{factoryName}/pipelines/{pipelineName}/createRun
  ?api-version=2018-06-01

No notification is sent to any team. The flow logs the event to Dataverse and exits. If the retry also fails, ADF will send another alert email and the flow will trigger again. After two consecutive transient failures for the same pipeline within a one-hour window, a condition in the run history analysis upgrades the routing to the Medium severity branch rather than attempting a third automatic retry.

Branch B: Medium Severity (Teams Approval)

Schema changes, data issues, and transient failures below the confidence threshold all land here. The flow posts a custom Adaptive Card to a designated Teams channel using the Teams connector's Post an Adaptive Card and wait for a response action. The card body includes the pipeline name, the AI's probable cause sentence, the category, the confidence score, and the recommended action, with two custom buttons: Approve Fix and Escalate to On-Call. The flow reads the approver's choice from the action's own output, such as outputs('Post_an_Adaptive_Card_and_wait_for_a_response')?['body/data/action'], since this pattern doesn't route through the Approvals connector at all.

If your organization prefers Dataverse-backed approval records with built-in audit history over a hand-authored Adaptive Card, the Start and wait for an approval action is the alternative worth considering: it is a Standard connector action that automatically creates the Dataverse approval record and lets approvers respond from Outlook, Teams (via the built-in Approvals app), or the Power Automate action center. The trade-off is that its card format and button labels come from the Approval Type you select rather than being freely customizable, and its result is read differently: outputs('Start_and_wait_for_an_approval')?['body/outcome'], than the custom Adaptive Card path above. Build one pattern or the other per flow rather than mixing them, since they produce differently shaped outputs for the downstream Condition and logging steps.

One important operational constraint applies to either approach: Power Automate cloud flow runs have a hard maximum duration of 30 days from the moment the flow is triggered. An approval request that remains unanswered for 30 days will cause the flow run to fail with a timeout error rather than expire gracefully. For pipeline failure approvals, this is rarely a practical concern because unanswered approval requests at that timescale represent a process failure. However, teams with strict audit requirements may prefer to implement the decoupled two-flow approval pattern: Flow 1 creates the approval record (via Create an approval (v2)) and exits; Flow 2 is triggered by a Dataverse row update when the approver responds, ensuring neither flow holds a 30-day thread open.

Branch C: High Severity or Low Confidence (On-Call Page)

Permissions errors, unknown categories, and any failure where confidence is below 0.50 go here. The flow sends an email to the on-call distribution list with the full AI analysis JSON formatted as a readable table, the original ADF error message, and a direct link to the ADF monitoring run. If your team uses PagerDuty or Opsgenie, an HTTP action can call their API to open a high-priority incident instead of or in addition to the email.

Guardrail principle: The AI analysis result is advisory only. No branch triggers a destructive operation autonomously. The auto-retry in Branch A calls the pipeline rerun endpoint, which is a safe idempotent read-and-requeue operation because retry_safe is verified first. No branch drops, truncates, or modifies the affected table without explicit human approval. The allowed action list for autonomous execution is exactly one item: pipeline rerun. Everything else requires a human in the loop.

Step 4: Validate AI Output Before Routing

The Parse JSON action will fail if the AI returns malformed JSON or omits a required field. Wrap the entire AI analysis and Parse JSON block in a Scope configured as a Try scope. Create a parallel Catch scope configured to run when the Try scope has failed, timed out, or been skipped. Inside the Catch scope, the flow routes directly to the on-call path with an error message indicating that the AI analysis itself failed, not the original pipeline. This ensures that an AI Builder outage or credit depletion never silently drops a pipeline failure alert.

Additionally, after the Parse JSON step succeeds, add a Condition action that validates the category value against a predefined list before entering the Switch. This can be expressed as a Power Automate expression:

// Condition expression: validate category is in the allowed list
contains(
  createArray('TRANSIENT','SCHEMA_CHANGE','PERMISSIONS','DATA_ISSUE','UNKNOWN'),
  body('Parse_AI_Response')?['category']
)

If this condition is false, the flow skips the Switch entirely and routes to the on-call path. This guards against the AI returning a category that is semantically reasonable but not in the enumeration, such as "INFRASTRUCTURE" or "CAPACITY_LIMIT," which would otherwise fall through the Switch's default case silently.

Step 5: Log Everything to Dataverse

Every flow execution, regardless of which branch it takes, should write one record to a Dataverse table. The table schema should include at minimum the following columns:

Column Type Source
PipelineName Text Parsed from alert email subject
FailureTimestamp DateTime Email received time
ErrorMessage Text (long) Parsed from alert email body
AI_Category Choice AI JSON output: category field
AI_Severity Choice AI JSON output: severity field
AI_Confidence Decimal AI JSON output: confidence field
AI_ProbableCause Text AI JSON output: probable_cause field
ActionTaken Choice Which branch executed: AutoRetry / TeamsApproval / OnCallPage / AIFailed
ApproverName Text Approval response metadata (Branch B only)
ApproverDecision Choice Approve / Escalate (Branch B only)
ResolutionTimestamp DateTime When the flow completed or the approval was received
AI_ClassificationOverridden Yes/No True if approver selected Escalate despite AI routing to Branch B

The AI_ClassificationOverridden column is especially important for the measurement report. When an approver selects "Escalate to On-Call" on a card that the AI categorized as Medium severity, that decision signals that the AI's classification was incorrect or insufficient for the situation. Tracking this override rate over time provides the ground-truth feedback necessary to refine the prompt.

Step 6: Measure Whether the AI Was Right

The Dataverse log table feeds directly into a Power BI report that answers the questions that justify the investment in building this flow. The most important metrics are not the ones that make the flow look good; they are the ones that reveal where it needs improvement.

Metric 1: Auto-Resolution Rate

The percentage of pipeline failures that the flow resolved without human involvement (Branch A executions where the auto-retry succeeded). A high rate confirms that the transient classification is accurate. A low rate may indicate that the confidence threshold is set too conservatively, or that the pipeline's failure modes are genuinely diverse and require human judgment more often than expected.

Metric 2: Mean Time to Resolution (MTTR)

The difference between FailureTimestamp and ResolutionTimestamp for each record. Segment this by ActionTaken to see the median resolution time for auto-retried failures versus approved-then-fixed failures versus on-call pages. The goal is not to minimize MTTR universally but to ensure that the fastest resolution path (auto-retry) is applied to the largest share of failures that genuinely warrant it.

Metric 3: AI Classification Override Rate

The percentage of Branch B cases where the approver selected "Escalate to On-Call" rather than approving the AI's recommended action. An override rate above 20 percent on a stable pipeline portfolio suggests that the prompt's category definitions or the confidence threshold require adjustment. Each override is also a labeled training example: the error message, the AI's classification, and the human's correction form a dataset for prompt refinement.

Metric 4: AI Analysis Failure Rate

The percentage of flow runs that hit the Catch scope because the AI action itself failed, typically due to credit depletion or a malformed JSON response. This metric monitors the reliability of the AI Builder infrastructure and flags when credit allocation needs to be increased in the Power Platform Admin Center.

Building this report as a live Power BI dataset connected to Dataverse via DirectQuery means the operational team can monitor these metrics in near real time without scheduled refreshes. A monthly review of the override rate and category distribution should drive quarterly prompt revisions as the pipeline portfolio changes and new failure modes emerge.

What This Approach Does Well and Where It Falls Short

The architecture described in this post delivers genuine operational value across several dimensions. Engineers are no longer paged for routine transient failures at 3am. Medium-severity failures receive structured context rather than a raw stack trace, which accelerates human decision-making even when a human remains in the loop. The Dataverse log creates an auditable record of every AI recommendation and every human override, which is a meaningful improvement over the informal email threads and Slack messages that previously constituted incident history. The measurement report closes the feedback loop, treating AI classification accuracy as an operational KPI rather than an assumption.

However, several limitations are worth stating plainly. The Run a Prompt action's AI Builder model is a general-purpose language model, not a model trained on your organization's pipeline history. Its classification accuracy for novel failure modes or organization-specific error codes will be lower than its accuracy for common, well-described failure patterns. The confidence score it returns is the model's self-reported uncertainty, which is not a calibrated probability; a reported confidence of 0.85 does not mean the classification is correct 85 percent of the time, and the threshold values in the routing logic should be validated empirically against your own incident log before treating them as production-ready defaults.

Additionally, the flow's email trigger introduces a dependency on ADF's alert email format, which is subject to change with product updates. A more resilient trigger would use ADF's native webhook or Event Grid integration to send a structured JSON payload directly to a Power Automate HTTP trigger, eliminating the need to parse free-text email bodies. Teams that want to invest in a more durable architecture should consider that path before scaling this flow across a large pipeline portfolio.

The core insight this flow embodies is not that AI should make incident response decisions autonomously. It is that AI classification as one deterministic step inside a structured routing flow is a tractable, auditable, and immediately valuable use of AI in production operations. The flow is green or not based on its own execution logic. The AI is right or not based on the override data the log accumulates. Both can be monitored independently, and both improve over time through deliberate measurement rather than assumption.
