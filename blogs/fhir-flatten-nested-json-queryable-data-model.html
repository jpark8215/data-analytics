How to Flatten FHIR's Deeply Nested JSON into a Queryable Data Model

The step most tutorials skip: a practical Python guide to converting Patient and Observation resources into clean, denormalized tables that load into SQL, Microsoft Fabric Lakehouse, and Azure Synapse without schema drift.

Published: November 4, 2026

Every data engineer who encounters FHIR for the first time arrives with a reasonable assumption: JSON is straightforward, and flattening it into a relational table is a solved problem. That assumption collapses within minutes of inspecting a real Patient resource. A FHIR Patient carries a name array where each element itself contains a given array. Its telecom array holds multiple contact points of varying types. Its address array nests a line array inside each address record. And then there are extensions: a parallel array of arbitrary key-value pairs attached at any level of the document, keyed by URL rather than field name. Observation resources are structurally more severe still, because their primary value field changes its own key depending on the LOINC code category being recorded.

The official HL7 FHIR R4 specification defines nearly every element in the Patient resource with a cardinality of 0..*, meaning most fields are entirely optional and may repeat an unlimited number of times. This design is intentional and architecturally sound for interoperability. However, it creates a category of engineering problem that generic tutorials do not address: how to safely extract, normalize, and load these structures into SQL-queryable tables without data loss, schema drift errors, or silent null-column proliferation. This post works through that problem systematically, using Python, pandas, and jsonpath-ng against realistic FHIR R4 Bundle JSON.

Understanding the Nesting Problem Before Writing Any Code

A clear mental model of the nesting patterns is a prerequisite for designing a correct flattening strategy. FHIR resources exhibit three distinct nesting categories, each demanding a different engineering response.

The first category is the repeating scalar array. The Patient.name[].given field is a plain array of strings: ["Peter", "James"]. Flattening this naively by joining the array into a single comma-delimited string is tempting but destroys downstream queryability. The correct approach is to select a single representative value using a priority rule, or to persist the full array in a child dimension table linked by a foreign key.

The second category is the repeating object array. Patient.telecom is an array of ContactPoint objects, each containing its own system, value, and use sub-fields. A patient may have a home phone, a work phone, and an email address simultaneously. Collapsing these into a single row via a cross-join without filtering by use first produces a Cartesian multiplication of rows that silently corrupts counts in any downstream aggregate query.

The third category, and the most disruptive, is the polymorphic choice element. The Observation resource defines a value[x] field where the actual JSON key changes based on the data type being stored. A heart-rate observation carries valueQuantity; a discharge-disposition observation carries valueCodeableConcept; a free-text note carries valueString. A fixed-schema table definition cannot accommodate all three under a single column name. Any extraction logic that hard-codes resource["valueQuantity"] will raise a KeyError on any other Observation type and fail silently if the caller uses .get() without fallback handling.

Setting Up the Environment

The flattening pipeline demonstrated in this post requires three libraries. Install them with pip before proceeding.

pip install pandas jsonpath-ng requests

The jsonpath-ng library provides JSONPath expression parsing that aims for RFC 9535 alignment, and it's useful for declaratively expressing filter-style lookups — such as finding a specific typed identifier inside an array by matching a field value — that would otherwise require a manual loop. Most of the flattening logic in this post still relies on straightforward Python dict and list traversal, since FHIR's resource shapes are varied enough that explicit, readable loops are often clearer than deeply chained JSONPath expressions; jsonpath-ng is reached for selectively rather than everywhere. Note also that its filter syntax is an extension feature — it requires importing parse from jsonpath_ng.ext rather than the base package, as shown below. The standard library json module handles deserialization. All examples below target data retrieved from the public SMART Health IT FHIR R4 sandbox at https://r4.smarthealthit.org, which serves synthetic patient data under no authentication requirement and is therefore suitable for prototyping and testing.

Step 1: Fetching and Parsing a FHIR Bundle

FHIR servers deliver paginated search results as Bundle resources. Each Bundle wraps an entry array, and each entry object nests the actual clinical resource inside a resource key. The first engineering task is to reliably extract the resource array from every page of results.

import requests
import json
import pandas as pd
from jsonpath_ng.ext import parse

BASE_URL = "https://r4.smarthealthit.org"

def fetch_all_resources(resource_type: str, params: dict = None, max_records: int = 500) -> list:
    """Fetch up to max_records of a FHIR resource type, returning a flat list of resource dicts.

    A cap is enforced by default because r4.smarthealthit.org is a shared, public,
    unauthenticated sandbox: following every 'next' link with no limit can pull far
    more data than intended and puts unnecessary load on a community resource.
    """
    resources = []
    url = f"{BASE_URL}/{resource_type}"
    query = params or {"_count": 50}

    while url and len(resources) < max_records:
        response = requests.get(url, params=query, timeout=30)
        response.raise_for_status()
        bundle = response.json()

        # Extract resource objects from each entry
        for entry in bundle.get("entry", []):
            resource = entry.get("resource", {})
            if resource:
                resources.append(resource)
            if len(resources) >= max_records:
                break

        # Follow the 'next' link for pagination
        url = None
        query = {}  # params only needed on first request
        for link in bundle.get("link", []):
            if link.get("relation") == "next":
                url = link.get("url")
                break

    return resources

patients_raw = fetch_all_resources("Patient")
print(f"Fetched {len(patients_raw)} Patient resources")

Note on pagination: FHIR Bundle resources include a link array. The entry with "relation": "next" provides the URL for the subsequent page. Always consume all pages before beginning transformation; a partial dataset produces misleading aggregate results when loaded into a reporting layer. Pair this with a sensible max_records cap on a shared public sandbox, so "consume all pages" means all pages of your intended cohort, not an unbounded crawl of the entire server.

Step 2: Flattening the Patient Resource

The Patient resource contains four structurally distinct nesting levels that each require a separate extraction strategy: the root-level scalar fields, the name array of HumanName objects, the telecom array of ContactPoint objects, and the address array of Address objects. The correct approach is to produce one primary dimension table and one child table per multi-valued array.

Extracting Root-Level Scalar Fields

Root-level scalar fields such as id, gender, and birthDate are straightforward. The complexity begins immediately when extracting the Medical Record Number from the identifier array, which contains typed identifier objects. Using jsonpath-ng's filter extension allows declarative extraction without fragile index assumptions — remembering that filter expressions require an @. prefix on the field being tested and parentheses around the whole condition. 

def extract_patient_core(resource: dict) -> dict:
    """Extract flat scalar fields from a single Patient resource dict."""

    # Build a JSONPath expression to find the MRN identifier by system URL.
    # Filter expressions are a jsonpath_ng.ext feature: the tested field needs
    # an `@.` prefix, and the condition needs enclosing parentheses.
    mrn_expr = parse("identifier[?(@.system = 'http://hospital.org/mrns')].value")
    mrn_matches = [m.value for m in mrn_expr.find(resource)]
    mrn = mrn_matches[0] if mrn_matches else None

    # Select the official name, falling back to the first name in the array
    official_name = None
    for name_obj in resource.get("name", []):
        if name_obj.get("use") == "official":
            official_name = name_obj
            break
    if official_name is None and resource.get("name"):
        official_name = resource["name"][0]

    family = official_name.get("family") if official_name else None
    given_list = official_name.get("given", []) if official_name else []
    # Join multiple given names with a space; store separately if queryability is needed
    given = " ".join(given_list) if given_list else None

    return {
        "patient_id": resource.get("id"),
        "mrn": mrn,
        "family_name": family,
        "given_name": given,
        "gender": resource.get("gender"),
        "birth_date": resource.get("birthDate"),
        # FHIR defines no default for Patient.active when the field is absent.
        # Treating a missing value as True is a pipeline-level assumption, not
        # a spec requirement — confirm it matches your source system's
        # convention before relying on it downstream.
        "active": resource.get("active", True),
    }

patient_core_rows = [extract_patient_core(p) for p in patients_raw]
df_patient = pd.DataFrame(patient_core_rows)
print(df_patient.dtypes)

Producing a Child Table for Telecom and Address

Telecom and address data must never be flattened into the same row as the core patient record using a join, because doing so produces one row per telecom per address per patient. A patient with two phone numbers and two addresses would generate four rows in the core table, quadrupling every aggregate count. Instead, extract them into separate grain-specific child tables linked by patient_id.

def extract_patient_telecom(resource: dict) -> list:
    """Return one row dict per telecom entry for this patient."""
    patient_id = resource.get("id")
    rows = []
    for contact in resource.get("telecom", []):
        rows.append({
            "patient_id": patient_id,
            "system": contact.get("system"),    # phone | fax | email | url | sms
            "value": contact.get("value"),
            "use": contact.get("use"),          # home | work | temp | old | mobile
            "rank": contact.get("rank"),
        })
    return rows

def extract_patient_address(resource: dict) -> list:
    """Return one row dict per address entry for this patient."""
    patient_id = resource.get("id")
    rows = []
    for addr in resource.get("address", []):
        # address.line is itself an array of street address strings
        line = " ".join(addr.get("line", []))
        rows.append({
            "patient_id": patient_id,
            "use": addr.get("use"),             # home | work | temp | old | billing
            "address_type": addr.get("type"),   # postal | physical | both
            "line": line,
            "city": addr.get("city"),
            "state": addr.get("state"),
            "postal_code": addr.get("postalCode"),
            "country": addr.get("country"),
        })
    return rows

# Build child DataFrames from all patients
telecom_rows = []
address_rows = []
for p in patients_raw:
    telecom_rows.extend(extract_patient_telecom(p))
    address_rows.extend(extract_patient_address(p))

df_telecom = pd.DataFrame(telecom_rows)
df_address = pd.DataFrame(address_rows)

print(f"Core patients:  {len(df_patient)} rows")
print(f"Telecom entries: {len(df_telecom)} rows")
print(f"Address entries: {len(df_address)} rows")

Handling Extensions Safely

Extensions present the most opaque challenge because their structure is keyed by arbitrary URL strings rather than stable JSON field names. The HL7 FHIR R4 specification allows every resource and data type to carry a parallel extension array at any nesting level. Common US Core extensions include race, ethnicity, and birth sex. Extracting a specific extension requires matching on its URL and then reading whichever value[x] sub-field the extension author chose.

def extract_extension_by_url(resource: dict, url: str) -> any:
    """Extract the first value from a root-level extension matching the given URL."""
    for ext in resource.get("extension", []):
        if ext.get("url") == url:
            # Extensions use the same value[x] polymorphism as Observation
            # Try each possible value key in order of likelihood
            for key in ("valueCode", "valueString", "valueCoding",
                        "valueBoolean", "valueInteger", "valueAddress"):
                if key in ext:
                    val = ext[key]
                    # If the value is itself a complex object, extract display text
                    if isinstance(val, dict):
                        return val.get("display") or val.get("code") or str(val)
                    return val
    return None

# Example: extract US Core birth-sex extension for each patient
BIRTH_SEX_URL = "http://hl7.org/fhir/us/core/StructureDefinition/us-core-birthsex"
df_patient["birth_sex"] = [
    extract_extension_by_url(p, BIRTH_SEX_URL) for p in patients_raw
]

Step 3: Flattening the Observation Resource

The Observation resource is architecturally more complex than Patient because its primary value is polymorphic, its component array can contain nested sub-observations, and its referenceRange array may carry multiple population-specific bounds. Each of these patterns requires a distinct extraction function.

Resolving the value[x] Polymorphism

The FHIR specification defines the Observation value as a choice of eleven possible types. The JSON key changes with each type: valueQuantity for a numeric measurement, valueCodeableConcept for a coded result, valueString for a free-text result, valueBoolean for a binary result, and so forth. A production-grade extraction function must check for all variants and map them to consistent output columns.

VALUE_X_KEYS = [
    "valueQuantity",
    "valueCodeableConcept",
    "valueString",
    "valueBoolean",
    "valueInteger",
    "valueRange",
    "valueRatio",
    "valueSampledData",
    "valueTime",
    "valueDateTime",
    "valuePeriod",
]

def resolve_value_x(resource: dict, prefix: str = "") -> dict:
    """
    Detect which value[x] key is present and normalize to consistent columns.
    Works for both root Observation and nested component objects.
    prefix: optional string to disambiguate component columns from root columns.
    """
    result = {
        f"{prefix}value_type": None,
        f"{prefix}value_num": None,
        f"{prefix}value_unit": None,
        f"{prefix}value_string": None,
        f"{prefix}value_code": None,
    }

    for key in VALUE_X_KEYS:
        if key not in resource:
            continue

        val = resource[key]
        type_label = key.replace("value", "", 1)  # e.g., "Quantity", "CodeableConcept"
        result[f"{prefix}value_type"] = type_label

        if key == "valueQuantity":
            result[f"{prefix}value_num"] = val.get("value")
            result[f"{prefix}value_unit"] = val.get("unit")
            result[f"{prefix}value_code"] = val.get("code")

        elif key == "valueCodeableConcept":
            codings = val.get("coding", [])
            if codings:
                result[f"{prefix}value_code"] = codings[0].get("code")
                result[f"{prefix}value_string"] = codings[0].get("display")
            result[f"{prefix}value_string"] = result[f"{prefix}value_string"] or val.get("text")

        elif key in ("valueString", "valueTime", "valueDateTime"):
            result[f"{prefix}value_string"] = str(val)

        elif key == "valueBoolean":
            result[f"{prefix}value_string"] = "true" if val else "false"

        elif key == "valueInteger":
            result[f"{prefix}value_num"] = float(val)

        elif key == "valueRange":
            # Store low and high as a text representation
            low = val.get("low", {}).get("value")
            high = val.get("high", {}).get("value")
            result[f"{prefix}value_string"] = f"{low}-{high}"
            result[f"{prefix}value_unit"] = val.get("low", {}).get("unit")

        break  # Only one value[x] key will ever be present per resource

    return result

Extracting the Core Observation Row

def extract_observation_core(resource: dict) -> dict:
    """Extract a flat row dict from a single Observation resource."""

    # Extract the LOINC code from the nested code.coding array
    loinc_code = None
    loinc_display = None
    for coding in resource.get("code", {}).get("coding", []):
        if "loinc.org" in coding.get("system", ""):
            loinc_code = coding.get("code")
            loinc_display = coding.get("display")
            break

    # Extract subject patient reference (format: "Patient/abc123")
    subject_ref = resource.get("subject", {}).get("reference", "")
    patient_id = subject_ref.split("/")[-1] if "/" in subject_ref else None

    row = {
        "observation_id": resource.get("id"),
        "patient_id": patient_id,
        "status": resource.get("status"),
        "loinc_code": loinc_code,
        "loinc_display": loinc_display,
        "effective_datetime": resource.get("effectiveDateTime")
                              or resource.get("effectivePeriod", {}).get("start"),
        "issued": resource.get("issued"),
    }

    # Merge the resolved value[x] columns into the row
    row.update(resolve_value_x(resource))

    # Interpretation: coded result such as "H" (high), "L" (low), "N" (normal)
    interpretations = resource.get("interpretation", [])
    if interpretations:
        interp_codings = interpretations[0].get("coding", [])
        row["interpretation_code"] = interp_codings[0].get("code") if interp_codings else None
    else:
        row["interpretation_code"] = None

    return row

observations_raw = fetch_all_resources("Observation", {"_count": 100})
obs_core_rows = [extract_observation_core(o) for o in observations_raw]
df_observation = pd.DataFrame(obs_core_rows)
print(df_observation[["observation_id", "loinc_code", "value_type", "value_num", "value_unit"]].head(10))

Extracting Components and Reference Ranges into Child Tables

The component array appears most often in vital-sign Observations. A blood pressure Observation, for example, carries systolic pressure as one component and diastolic pressure as a second component, each with its own LOINC code and valueQuantity. These must be extracted into a child table rather than flattened as wide columns on the parent row, because the number of components varies across LOINC codes.

def extract_observation_components(resource: dict) -> list:
    """Return one row dict per component for this observation."""
    obs_id = resource.get("id")
    rows = []
    for idx, comp in enumerate(resource.get("component", [])):
        comp_codings = comp.get("code", {}).get("coding", [])
        comp_loinc = comp_codings[0].get("code") if comp_codings else None
        comp_display = comp_codings[0].get("display") if comp_codings else None
        row = {
            "observation_id": obs_id,
            "component_index": idx,
            "component_loinc": comp_loinc,
            "component_display": comp_display,
        }
        row.update(resolve_value_x(comp))
        rows.append(row)
    return rows

def extract_observation_reference_ranges(resource: dict) -> list:
    """Return one row dict per referenceRange entry for this observation."""
    obs_id = resource.get("id")
    rows = []
    for rr in resource.get("referenceRange", []):
        low_obj = rr.get("low", {})
        high_obj = rr.get("high", {})
        rows.append({
            "observation_id": obs_id,
            "range_text": rr.get("text"),
            "low_value": low_obj.get("value"),
            "low_unit": low_obj.get("unit"),
            "high_value": high_obj.get("value"),
            "high_unit": high_obj.get("unit"),
        })
    return rows

component_rows = []
ref_range_rows = []
for o in observations_raw:
    component_rows.extend(extract_observation_components(o))
    ref_range_rows.extend(extract_observation_reference_ranges(o))

df_components = pd.DataFrame(component_rows)
df_ref_ranges = pd.DataFrame(ref_range_rows)
print(f"Observation components:   {len(df_components)} rows")
print(f"Reference range entries:  {len(df_ref_ranges)} rows")

Step 4: Loading into SQL, Fabric Lakehouse, or Synapse

The five DataFrames produced above represent a stable, queryable star schema that loads cleanly into any relational or lakehouse destination. The loading strategy differs slightly across targets, but the DataFrame structure itself requires no further transformation.

Loading into a SQL Database via SQLAlchemy

from sqlalchemy import create_engine

# Example connection string for Azure SQL or SQL Server
engine = create_engine(
    "mssql+pyodbc://user:password@server/database?driver=ODBC+Driver+18+for+SQL+Server"
)

# Use if_exists='replace' during development; switch to 'append' for incremental loads
df_patient.to_sql("dim_patient", engine, if_exists="replace", index=False)
df_telecom.to_sql("dim_patient_telecom", engine, if_exists="replace", index=False)
df_address.to_sql("dim_patient_address", engine, if_exists="replace", index=False)
df_observation.to_sql("fact_observation", engine, if_exists="replace", index=False)
df_components.to_sql("obs_component", engine, if_exists="replace", index=False)
df_ref_ranges.to_sql("obs_reference_range", engine, if_exists="replace", index=False)

Writing to Microsoft Fabric Lakehouse via Delta Tables

In Microsoft Fabric Lakehouse and Azure Synapse Analytics, the preferred loading target is a Delta table in the Files or Tables section of the Lakehouse. When running this pipeline inside a Fabric Notebook, the Spark session is pre-configured and the DataFrame can be written directly using the Spark writer API after converting from pandas.

# Inside a Microsoft Fabric Notebook or Azure Synapse Notebook
# spark is provided automatically as a global variable

from pyspark.sql import SparkSession

# Convert pandas DataFrames to Spark DataFrames
spark_patient      = spark.createDataFrame(df_patient)
spark_telecom      = spark.createDataFrame(df_telecom)
spark_observation  = spark.createDataFrame(df_observation)
spark_components   = spark.createDataFrame(df_components)

# Write as Delta tables into the Lakehouse
spark_patient.write.format("delta").mode("overwrite").saveAsTable("fhir.dim_patient")
spark_telecom.write.format("delta").mode("overwrite").saveAsTable("fhir.dim_patient_telecom")
spark_observation.write.format("delta").mode("overwrite").saveAsTable("fhir.fact_observation")
spark_components.write.format("delta").mode("overwrite").saveAsTable("fhir.obs_component")

Schema drift prevention: Delta Lake's schema-auto-merge is disabled by default, so strict schema enforcement on mode("append") writes is already the baseline behavior. Setting spark.conf.set("spark.databricks.delta.schema.autoMerge.enabled", "false") explicitly reaffirms that default rather than adding new protection — it's still worth doing so the intent is visible in code and survives a workspace- or session-level override elsewhere in the notebook. One naming note: this key carries the spark.databricks prefix because it originates from Delta Lake's Databricks lineage; Fabric's Spark runtime honors it through open-source Delta Lake compatibility rather than it being a Fabric-native setting. With auto-merge off, a write that introduces an unexpected column fails immediately, surfacing data quality issues before they silently widen the table.

Practical Trade-Offs: What This Approach Gets Right and Where It Breaks

The pandas-plus-jsonpath-ng extraction strategy is well-suited to development, testing, and modest production cohorts. It runs entirely in a standard Python environment without requiring a Spark cluster, executes deterministically, and produces DataFrames that any analyst can inspect with standard tooling. For cohorts of up to several hundred thousand FHIR resources, the memory footprint is manageable on a reasonably provisioned VM or notebook kernel.

However, this architecture carries meaningful limitations that mature production implementations must address.

Dimension Strength Limitation
Scalability No cluster infrastructure required; runs in any Python environment. Pandas holds all data in memory. Cohorts exceeding several million resources require chunked reading or a Spark-based alternative.
Polymorphism handling The resolve_value_x function covers all eleven FHIR value types with consistent output columns. New FHIR R5 value types or custom extensions introduced by specific EHR vendors may add value key variants not covered by the current enumeration.
Extension extraction URL-keyed extraction is explicit and auditable. Implementation-specific extension URLs vary across Epic, Oracle Health, and Meditech deployments; extraction functions must be adapted per data source.
Incremental loading The if_exists="append" mode supports incremental writes. FHIR does not guarantee unique resource IDs across servers. Deduplication logic based on resource.id plus source system is required before appending.
Cardinality correctness Producing separate child tables per array avoids Cartesian row multiplication. Multi-table architecture requires analysts to understand foreign key joins; a single wide table is more accessible but statistically misleading for multi-valued attributes.

Moving Toward a Production Pipeline

Organizations moving these functions beyond prototyping should consider three architectural upgrades. First, the extraction functions demonstrated here operate synchronously on a single resource at a time. A production pipeline should wrap them in a chunked iterator that reads FHIR NDJSON (newline-delimited JSON) from Bulk Data exports rather than paginated REST API responses. NDJSON files produced by the FHIR Bulk Data Access specification ($export operation) can be streamed line-by-line, enabling constant-memory processing regardless of cohort size.

Second, the jsonpath-ng expressions and field mappings in this post are correct for FHIR R4 base resources. US Core 7.0 implementation guides and Epic-specific profiles may impose additional constraints or add must-support extensions that require supplementary extraction logic. Validating the output DataFrames against known record counts from the source system after each pipeline run is a necessary operational control.

Third, loading into Microsoft Fabric Lakehouse using Delta format introduces an important governance opportunity. Delta table history and time-travel capabilities allow the pipeline to retain prior versions of flattened data, enabling point-in-time audits that satisfy HIPAA data integrity requirements. Combining Delta with Unity Catalog column-level access controls allows the same physical tables to serve both clinical analysts with full patient context and population health researchers with de-identified cohort views.
