Call a REST API Directly from T-SQL: sp_invoke_external_rest_endpoint in SQL Server 2025

SQL Server 2025 ships a system stored procedure that calls an HTTPS endpoint from pure T-SQL. Here is how to enable it, how the response envelope works, and what the preview-stage limits mean for production use.

Published: November 9, 2026

For more than two decades, pulling data from an external HTTP API into SQL Server required an intermediary. Developers assembled SSIS packages, wrote CLR assemblies, spawned Python scripts via xp_cmdshell, or built dedicated ETL services that consumed the API separately and then inserted rows through a database connection. Each of those approaches introduced a deployment surface outside the database engine itself, complicating operational ownership and permission auditing. SQL Server 2025 addresses this directly with the system stored procedure sys.sp_invoke_external_rest_endpoint, which invokes an HTTPS REST endpoint from within a T-SQL batch and returns the HTTP response body as an output variable that subsequent T-SQL can parse with OPENJSON.

The feature was first available in Azure SQL Database and Azure SQL Managed Instance, where Microsoft demonstrated its use for calling Azure OpenAI, Azure Functions, and custom web APIs without leaving the database tier. SQL Server 2025 brings the same capability to on-premises and self-managed instances, with one important distinction: unlike Azure SQL, where the feature is available by default, SQL Server 2025 ships with external REST endpoint invocation disabled. A deliberate sp_configure step is required before any call can be made. This post walks through that activation sequence, the full procedure signature, authenticated and unauthenticated call patterns, response parsing, and an honest assessment of the limitations that remain while the feature is in preview on SQL Server 2025.

What the Procedure Actually Does

The procedure sys.sp_invoke_external_rest_endpoint instructs the SQL Server engine to open an outbound HTTPS connection from the host operating system to the URL you specify, transmit an optional JSON payload, and capture the HTTP response into an output parameter of type NVARCHAR(MAX). The call is synchronous: the executing T-SQL batch waits for the HTTP response before continuing. The response body is not returned as a result set directly; it is placed into the output variable you declare, and you then use OPENJSON or JSON_VALUE to shred it into rows and columns.

The full procedure signature accepts more than the handful of parameters most examples show. Alongside @url, @payload, @headers, @method, and @response, the procedure also supports @timeout (a positive smallint in seconds, default 30, accepted range 1–230), @credential (the name of a Database Scoped Credential to use for the call), and @retry_count (a positive tinyint from 0 to 10, default 0, controlling automatic retries). @method accepts six values, not five: GET, POST, PUT, PATCH, DELETE, and HEAD, and if omitted defaults to POST.

The procedure wraps the actual API response inside its own JSON envelope before writing it to the output variable. The outer object contains a response node with the HTTP status code and response headers, and a result node that holds the raw payload the external API returned. This means any OPENJSON path expression targeting API data must navigate through $.result rather than the root of the JSON document.

Step 1: Enabling the Feature on SQL Server 2025

On SQL Server 2025, the external REST endpoint feature is controlled by a named server configuration option. It is set to 0 (disabled) after a fresh installation. Enabling it requires the sysadmin or serveradmin fixed server role, or the ALTER SETTINGS server-level permission directly, and the change takes effect immediately without a service restart.

-- Verify the current state before making any changes
EXEC sp_configure 'external rest endpoint enabled';
GO

-- Enable outbound REST calls from T-SQL
EXEC sp_configure 'external rest endpoint enabled', 1;
RECONFIGURE WITH OVERRIDE;
GO

-- Confirm the change applied
SELECT name, value_in_use
FROM sys.configurations
WHERE name = 'external rest endpoint enabled';
GO

Preview status on SQL Server 2025: As of the SQL Server 2025 release, this feature carries a preview designation on the on-premises engine. Microsoft's official documentation notes that preview features may have behavioral differences from the generally available Azure SQL implementation and are subject to change before general availability. Organizations should not enable this feature on production instances without evaluating the security implications described later in this post.

Step 2: Granting Execute Permission to Database Users

Enabling the feature at the server level does not automatically grant all users the ability to invoke external endpoints. Each database principal that needs to call the procedure must receive an explicit permission grant. The permission EXECUTE ANY EXTERNAL ENDPOINT controls this access and should be granted narrowly, following the principle of least privilege.

USE YourDatabaseName;
GO

-- Grant to a specific application service account only
GRANT EXECUTE ANY EXTERNAL ENDPOINT TO [app_service_account];
GO

-- Confirm active grants.
-- EXECUTE ANY EXTERNAL ENDPOINT is a database-level permission (class_desc = 'DATABASE'),
-- not an object-level permission tied to the procedure itself, so this query does not
-- join to sys.objects at all -- a join on p.major_id = o.object_id would silently drop
-- these rows, since a database-level permission's major_id is 0.
SELECT dp.name           AS principal_name,
       dp.type_desc      AS principal_type,
       p.permission_name
FROM sys.database_permissions p
JOIN sys.database_principals dp ON p.grantee_principal_id = dp.principal_id
WHERE p.class_desc = 'DATABASE'
  AND p.permission_name = 'EXECUTE ANY EXTERNAL ENDPOINT';
GO

Using a stored Database Scoped Credential (covered in Step 4) requires a second, credential-specific grant beyond EXECUTE ANY EXTERNAL ENDPOINT. A principal who can execute the procedure but has not been granted REFERENCES on a given credential cannot use that credential — the call will fail rather than silently falling back to an unauthenticated request.

-- Required in addition to EXECUTE ANY EXTERNAL ENDPOINT, per credential object
GRANT REFERENCES ON DATABASE SCOPED CREDENTIAL::[https://api.example.com] TO [app_service_account];
GO

Step 3: Calling an Unauthenticated Public API

The simplest possible invocation targets a public endpoint that requires no authentication header. The procedure accepts the HTTP method as N'GET', N'POST', N'PUT', N'PATCH', N'DELETE', or N'HEAD' — six values in total, though only the first five are commonly used for data retrieval and submission. The @response parameter must be declared as an NVARCHAR(MAX) output variable before the call.

The example below calls the public JSONPlaceholder test API, which returns an array of synthetic todo records as JSON. No credential is required for this call, so the @credential parameter is simply omitted. After the call, the return code is checked for HTTP success, and the response is immediately parsed with OPENJSON and inserted into a staging table.

-- Create a staging table to hold the API results
DROP TABLE IF EXISTS #todos;
CREATE TABLE #todos (
    todo_id     INT,
    user_id     INT,
    title       NVARCHAR(500),
    is_complete BIT
);

DECLARE @ret      INT;
DECLARE @response NVARCHAR(MAX);

-- Invoke the external endpoint
EXEC @ret = sys.sp_invoke_external_rest_endpoint
    @url     = N'https://jsonplaceholder.typicode.com/todos',
    @method  = N'GET',
    @timeout = 30,
    @response = @response OUTPUT;

-- @ret contains the HTTP status code returned by the endpoint
IF @ret NOT BETWEEN 200 AND 299
BEGIN
    RAISERROR('REST call failed. HTTP status: %d. Details: %s', 16, 1,
              @ret, @response);
    RETURN;
END

-- Parse the $.result array into rows using OPENJSON with an explicit schema
INSERT INTO #todos (todo_id, user_id, title, is_complete)
SELECT todo_id, user_id, title, is_complete
FROM OPENJSON(@response, N'$.result')
WITH (
    todo_id     INT           N'$.id',
    user_id     INT           N'$.userId',
    title       NVARCHAR(500) N'$.title',
    is_complete BIT           N'$.completed'
);

SELECT TOP 10 * FROM #todos ORDER BY todo_id;
GO

Why $.result and not $: The procedure always wraps the external API's response body inside a result key within its own JSON envelope. If your OPENJSON expression targets $ directly, it will read the wrapper object rather than the API payload, returning one row for the entire response rather than the individual records you expect. Always use $.result as the root path when parsing with OPENJSON.

Azure SQL's endpoint allowlist does not apply here: Azure SQL Database and Azure SQL Managed Instance restrict this procedure to a documented allowlist of Azure service domains (Azure Functions, Azure OpenAI, Blob Storage, Event Hubs, and similar). Microsoft's documentation is explicit that this allowlist "only applies to Azure SQL Database and Azure SQL Managed Instance" — SQL Server 2025 on-premises has no equivalent built-in restriction, so any HTTPS endpoint with a trusted TLS certificate is reachable by default. This is precisely why the network-layer firewall controls described later in this post matter more for on-premises deployments than for Azure SQL.

Step 4: Calling an Authenticated API with Database Scoped Credentials

Most production APIs require authentication through an Authorization header, an API key header, or a subscription key. Hardcoding secrets directly into T-SQL procedure calls creates a persistent security risk: secrets appear in plan cache, Extended Events traces, and procedure text visible through sys.sql_modules. The correct pattern uses a Database Scoped Credential, where the credential name matches the target endpoint's URL (its protocol, fully-qualified domain, and a path at least as generic as the URLs it will be used for) and the secret contains the headers as a JSON object. 

-- Create the credential once per database, per target domain
-- The IDENTITY must be 'HTTPEndpointHeaders' for header injection to work
CREATE DATABASE SCOPED CREDENTIAL [https://api.example.com]
WITH IDENTITY = 'HTTPEndpointHeaders',
SECRET = N'{"Authorization":"Bearer your-token-here","x-api-version":"2026-01"}';
GO

Unlike @url, @method, or @payload, the credential is not resolved automatically from the call's URL. It must be passed explicitly via the @credential parameter on every invocation that needs it; the engine then injects the stored secret headers transparently before transmitting the request. A call that omits @credential goes out with no authentication applied, regardless of which credentials exist in the database.

DECLARE @ret      INT;
DECLARE @response NVARCHAR(MAX);

EXEC @ret = sys.sp_invoke_external_rest_endpoint
    @url        = N'https://api.example.com/v1/orders?status=pending',
    @method     = N'GET',
    @credential = [https://api.example.com],
    @timeout    = 60,
    @response   = @response OUTPUT;

IF @ret NOT BETWEEN 200 AND 299
BEGIN
    SELECT @ret AS http_status,
           JSON_VALUE(@response, '$.response.status.http.description') AS error_description;
    RETURN;
END

-- Insert pending orders directly into a production staging table
INSERT INTO stg.pending_orders (order_id, customer_id, order_date, total_amount, currency)
SELECT order_id, customer_id, order_date, total_amount, currency
FROM OPENJSON(@response, N'$.result.orders')
WITH (
    order_id      NVARCHAR(50)   N'$.id',
    customer_id   NVARCHAR(50)   N'$.customerId',
    order_date    DATE           N'$.createdAt',
    total_amount  DECIMAL(18,2)  N'$.amount.value',
    currency      CHAR(3)        N'$.amount.currency'
);
GO

Step 5: Sending Data with a POST Request

POST calls follow the same pattern, with the addition of the @payload parameter, which accepts an NVARCHAR(MAX) JSON string. When constructing the payload dynamically from query results, the FOR JSON PATH clause produces conforming JSON without requiring string concatenation, which avoids injection vulnerabilities and special-character escaping errors.

DECLARE @ret      INT;
DECLARE @response NVARCHAR(MAX);
DECLARE @payload  NVARCHAR(MAX);

-- Build the payload from a live query result using FOR JSON
SELECT @payload = (
    SELECT TOP 1
        order_id    AS orderId,
        customer_id AS customerId,
        total_amount AS amount
    FROM stg.pending_orders
    WHERE order_id = 'ORD-20261109-0042'
    FOR JSON PATH, WITHOUT_ARRAY_WRAPPER
);

EXEC @ret = sys.sp_invoke_external_rest_endpoint
    @url        = N'https://api.example.com/v1/orders/submit',
    @method     = N'POST',
    @credential = [https://api.example.com],
    @payload    = @payload,
    @timeout    = 60,
    @response   = @response OUTPUT;

SELECT @ret                                                     AS http_status,
       JSON_VALUE(@response, '$.result.submissionId')          AS submission_id,
       JSON_VALUE(@response, '$.response.status.http.code')    AS response_code;
GO

Reading the Response Envelope

Understanding the full structure of the response envelope is necessary for robust error handling. The outer response node is always present, regardless of whether the call succeeded. The result node contains the API's response body when present; it is absent when the API returns HTTP 204 (No Content) or when the response body is empty.

-- Inspect the full envelope structure to understand what any given API returns
DECLARE @ret      INT;
DECLARE @response NVARCHAR(MAX);

EXEC @ret = sys.sp_invoke_external_rest_endpoint
    @url     = N'https://jsonplaceholder.typicode.com/posts/1',
    @method  = N'GET',
    @timeout = 30,
    @response = @response OUTPUT;

-- Extract individual metadata fields from the envelope
SELECT
    @ret                                                                AS proc_return_code,
    JSON_VALUE(@response, '$.response.status.http.code')               AS http_status_code,
    JSON_VALUE(@response, '$.response.status.http.description')        AS http_description,
    JSON_VALUE(@response, '$.response.headers.Content-Type')           AS content_type,
    /* Navigate into the result node for actual payload fields */
    JSON_VALUE(@response, '$.result.id')                               AS post_id,
    JSON_VALUE(@response, '$.result.title')                            AS post_title,
    JSON_VALUE(@response, '$.result.body')                             AS post_body;
GO

Known Limitations and Preview-Stage Constraints

The feature delivers genuine architectural value, but several technical boundaries must be understood before designing production workflows around it. The limitations described here are documented across Microsoft's official reference documentation, community research, and security advisory publications as of 2026.

Constraint Category Specific Limitation Engineering Implication
Protocol HTTPS only. Plain HTTP endpoints are rejected regardless of network topology. All target APIs must expose a valid TLS certificate trusted by the SQL Server host OS. Self-signed certificates on internal services will cause connection failures unless explicitly added to the Windows certificate store.
Allowed Endpoints Azure SQL Database and Azure SQL Managed Instance restrict calls to a documented allowlist of Azure service domains. SQL Server 2025 on-premises has no equivalent built-in allowlist. Teams porting a workflow from Azure SQL to SQL Server 2025 on-premises gain the ability to call arbitrary HTTPS endpoints — which is a capability expansion, not a parity feature, and raises the stakes of the permission and network controls described later in this post.
Parameter Size The @url and @headers parameters are each capped at 4,000 characters as declared types. Beyond that, the combined size of all headers actually sent — your @headers value plus any credential-injected headers plus system-supplied headers — is capped at 8 KB, and the fully assembled URL (including any credential-injected query string) is capped at 8 KB. The @payload and @response use NVARCHAR(MAX), with payload size over the wire limited to 100 MB. Very long query strings or complex multi-header authentication schemes may exceed the URL and header size limits even when individual parameters look small, requiring redesign of the target API call or use of POST body instead of query parameters.
Synchronous Execution The call blocks the executing worker thread until the endpoint responds or the timeout expires. Slow or intermittent external APIs can cause lock contention and worker thread exhaustion when invoked from high-concurrency workloads. This pattern is unsuitable for row-by-row API calls within cursor loops over large datasets.
Timeout The @timeout parameter is measured in seconds, is a positive smallint, and accepts values from 1 to 230. This range is documented as applying to SQL Server 2025 on-premises as well as Azure SQL. Long-running API calls that approach the timeout boundary hold database locks open for the duration, which can cascade into application-level timeouts across unrelated sessions. 230 seconds is a hard ceiling, not a tunable maximum — workflows needing longer-running external calls must poll a status endpoint across multiple shorter invocations instead.
Retry Behavior The optional @retry_count parameter (0–10, default 0) automatically retries on HTTP 408, 429, 500, 502, 503, and 504, honoring a Retry-After header when present or falling back to exponential backoff. This covers transport-level retries only, not transactional retry semantics — a POST that partially succeeded on the external system before a retriable error occurred may be resubmitted, so idempotency on the receiving API matters when @retry_count is used for anything beyond GET requests.
No Async or Streaming There is no native mechanism to call the procedure asynchronously or to process a streaming response body incrementally. Large response payloads are captured in full into NVARCHAR(MAX) before any parsing occurs, consuming memory proportional to the response size within the executing session.
Preview Status On SQL Server 2025, the feature remains in preview at the time of publication, meaning behavioral changes are possible in subsequent Cumulative Updates. Critical workflows depending on this procedure should be tested after each Cumulative Update and against Microsoft's release notes to detect any breaking changes before they affect production.

Security Considerations That Cannot Be Overlooked

Security research published by SpecterOps in 2026 documented a threat model specific to this procedure that every SQL Server administrator should review before enabling it. Because the procedure issues outbound HTTPS requests directly from the database engine process, any principal with EXECUTE ANY EXTERNAL ENDPOINT permission can transmit database contents to an arbitrary internet endpoint. In an environment where SQL injection vulnerabilities exist in the application tier, an attacker who achieves query execution could use this procedure to exfiltrate rows from sensitive tables to an attacker-controlled server, bypassing network controls placed on the application layer.

Additionally, EXECUTE ANY EXTERNAL ENDPOINT is a database-level permission, not an object-level permission. Granting it to a user allows that user to call the procedure against any URL, not just a pre-approved allowlist — and, as noted above, SQL Server 2025 on-premises has no native equivalent of the Azure SQL allowlist to fall back on. Mitigating this requires network-layer controls: configuring the SQL Server host's outbound firewall rules to restrict HTTPS traffic to known, approved API destinations.

Using a stored credential requires the separate REFERENCES grant described in Step 2, which gives administrators a second control point: a principal can be allowed to call arbitrary unauthenticated endpoints without necessarily being able to use any of the organization's stored API credentials, or vice versa. Neither grant alone prevents data exfiltration via an unauthenticated POST, which is why the network-layer controls below remain necessary regardless of how credential access is scoped.

Hardcoded secrets risk: Never pass authentication tokens or API keys directly in the @payload or @headers parameters as literal string values. Doing so exposes the secret in Extended Events session captures, Query Store plan text, and sys.dm_exec_query_stats. Always use a Database Scoped Credential with IDENTITY = 'HTTPEndpointHeaders', referenced explicitly via the @credential parameter, so that secrets are stored encrypted in the database master key and injected transparently by the engine.

When This Pattern Makes Operational Sense

Despite the limitations and security considerations, the procedure addresses genuine use cases that previously required disproportionately complex infrastructure. Scheduled T-SQL Agent jobs that need to notify a webhook or push a summary payload to an internal alerting API are a natural fit: the call volume is low, the payload is small, and no external service deployment is needed. Stored procedures that look up reference data from a stable internal REST service during a batch run can avoid an entire ETL pipeline for data that changes infrequently.

Conversely, the procedure is poorly suited to real-time, row-level API enrichment patterns. Calling an external geocoding or classification API once per record inside a trigger or a cursor loop over millions of rows will block worker threads, generate network costs proportional to record volume, and produce latency characteristics incompatible with transactional workloads. Those patterns belong in an application tier with async HTTP client libraries, connection pooling, and retry logic that the database engine does not expose.

For teams already using Azure SQL Database or Managed Instance, the procedure is generally available rather than in preview, and the operational experience is well documented — though worth remembering that Azure SQL's endpoint allowlist constrains it to approved Azure service domains in a way that SQL Server 2025 on-premises does not. SQL Server 2025 on-premises brings the same interface to organizations that cannot or will not migrate to Azure SQL, and the activation path documented in this post is consistent with what Microsoft's own reference documentation describes. As cumulative updates move the feature toward general availability on SQL Server 2025, the remaining preview-stage constraints around behavioral stability are likely to narrow.
