Mirroring in Microsoft Fabric: How to Replicate Databricks or SQL Data into OneLake Without Duplicating It

A detailed examination of Microsoft Fabric Mirroring, analyzing how zero-ETL replication brings Databricks Unity Catalog and SQL Server data into OneLake without storage duplication, alongside its genuine limitations.

Published: August 13, 2026

One of the most persistent operational burdens in enterprise data architecture is the movement of data between systems. Every time an organization copies a SQL Server table into a data warehouse, or exports a Databricks Delta table into a separate analytics store, it incurs storage costs, pipeline maintenance overhead, and the ever-present risk of producing inconsistent copies of the same information. Microsoft Fabric Mirroring was introduced to address this specific problem by creating a near real-time, read-accessible representation of external data within OneLake without physically copying the underlying bytes. According to Microsoft's official product documentation on the Mirroring overview page at learn.microsoft.com, this feature is designed as a zero-ETL solution that eliminates the need for traditional extract, transform, and load pipelines when the goal is analytics access rather than data transformation.

Understanding what Mirroring actually does, how it differs from OneLake Shortcuts, and where it falls short is essential for any organization evaluating its place in a modern data architecture. The feature covers several source systems including Azure SQL Database, SQL Server, Azure Cosmos DB, Snowflake, and Azure Databricks, each with its own implementation approach and set of constraints. This article focuses primarily on the SQL Server and Azure Databricks paths, which represent the most common scenarios and the most consequential design decisions.

The Core Mechanism: What "No Duplication" Actually Means

The phrase "without duplicating it" requires precise qualification, because it means different things depending on which source system is in use. For SQL Server, Mirroring does physically replicate data into OneLake, but it does so in a highly optimized, incremental manner using Change Data Capture (CDC). The initial snapshot copies the data once, and subsequent changes are propagated continuously rather than through periodic full exports. The result is stored as Delta Parquet files inside a Fabric Lakehouse, consuming OneLake storage capacity. This is not zero-copy in the strictest sense, but it is zero-ETL in the sense that no pipeline engineering is required to move changes forward. Microsoft's documentation for SQL Server Mirroring confirms that SQL Server 2016 through 2022 rely on CDC-based change tracking, while SQL Server 2025 takes a more efficient approach by reading the transaction log directly through a change feed mechanism, avoiding the overhead of CDC's intermediate change tables altogether.

For Azure Databricks, the architecture is fundamentally different and more accurately described as zero-copy. When an organization creates a Mirrored Azure Databricks Catalog item in Fabric, the physical Delta Lake files remain in their original Azure Data Lake Storage Gen2 location. Fabric does not copy them. Instead, it replicates only the metadata from the Databricks Unity Catalog, including the catalog structure, schema definitions, and table locations, and constructs managed OneLake shortcuts that point back to those original storage paths. Queries executed against the mirrored tables in Fabric read directly from the Databricks-managed ADLS paths without any data movement. This distinction is consequential for cost planning: organizations mirroring from Databricks avoid doubled storage costs entirely, while those mirroring from SQL Server incur OneLake storage for the replicated Delta files.

Setting Up SQL Server Mirroring: Prerequisites and Configuration

SQL Server Mirroring requires several infrastructure conditions before configuration can proceed. The source SQL Server instance, whether on-premises or hosted in a virtual machine, must be version 2016 or later. Additionally, an on-premises data gateway or VNet data gateway must be installed and configured to establish a secure connection between the SQL Server environment and the Fabric workspace. Microsoft's tutorial documentation at learn.microsoft.com specifies that the gateway is required for all on-premises SQL Server sources regardless of version.

Configuration Overview for SQL Server Mirroring:

  1. Enable Change Data Capture on the source SQL Server database using the system stored procedure sys.sp_cdc_enable_db.
  2. Install and configure an on-premises data gateway on a server with network access to the SQL Server instance.
  3. In the Fabric portal, navigate to the workspace and select New, then Mirrored Database, then SQL Server.
  4. Provide the connection string, credentials, and select the gateway. Fabric will validate connectivity and display available databases and tables.
  5. Select the tables to mirror and confirm. Fabric begins an initial snapshot, after which incremental changes propagate continuously.
  6. An automatically generated SQL Analytics Endpoint becomes available, enabling read-only T-SQL queries against the mirrored data.

The automatically generated SQL Analytics Endpoint is a particularly significant feature. It allows BI developers and analysts to query the mirrored SQL Server tables using familiar T-SQL syntax without writing any pipeline code or configuring a separate SQL pool. Furthermore, Power BI reports connected to this endpoint can leverage Direct Lake mode when the underlying Delta files are involved, delivering higher query performance than traditional import or DirectQuery modes.

Setting Up Azure Databricks Mirroring: Unity Catalog and VNet Considerations

Mirroring Azure Databricks tables into Fabric requires that the source workspace have Unity Catalog enabled, as the mirroring mechanism depends on Unity Catalog's metadata APIs to discover and replicate catalog structure. External tables and managed tables stored in Delta format on Azure Data Lake Storage are eligible for mirroring. Databricks workspaces behind private endpoints are supported through VNet data gateways, which Fabric uses to establish a secure network path to the Unity Catalog APIs without exposing the workspace to the public internet.

Configuration Overview for Azure Databricks Mirroring:

  1. Confirm that the Databricks workspace has Unity Catalog enabled and that the tables to be mirrored are stored as managed or external Delta tables in Azure Data Lake Storage Gen2.
  2. If the Databricks workspace is behind a private endpoint, install and configure a VNet data gateway within the same VNet.
  3. In the Fabric portal, create a new item of type Mirrored Azure Databricks Catalog and provide the Databricks workspace URL along with authentication credentials.
  4. Select the Unity Catalog catalogs and schemas to include. Fabric creates managed shortcuts for each eligible table pointing to the original ADLS paths.
  5. The mirrored catalog item exposes an automatically created SQL Analytics Endpoint, allowing T-SQL queries against Databricks tables from within Fabric.

Because Fabric accesses the physical Delta files via managed shortcuts rather than maintaining its own copy, changes made in Databricks, including inserts, updates, and schema evolution, are reflected in Fabric queries without any synchronization delay. The metadata refresh cycle, during which Fabric checks for newly added or removed tables from the Unity Catalog, runs periodically rather than in real time. Consequently, a table newly created in Databricks may take several minutes to appear in the Fabric mirrored catalog view, even though queries against already-known tables reflect live data immediately.

Mirroring versus Shortcuts: Choosing the Right Integration Pattern

One of the most common points of confusion when evaluating Fabric Mirroring is its relationship to OneLake Shortcuts, which are a distinct and more lightweight integration mechanism. Understanding the differences is essential because selecting the wrong approach can introduce unnecessary complexity or miss important capabilities.

Characteristic Fabric Mirroring (Databricks) OneLake Shortcut
Data movement None; metadata-only replication with managed shortcuts None; virtual reference to external storage path
Catalog structure Full Unity Catalog hierarchy replicated into Fabric Single storage path or container referenced
SQL Analytics Endpoint Auto-generated; supports T-SQL queries immediately Requires manual Lakehouse or Warehouse integration
Direct Lake support Yes, enabling high-performance Power BI reports Yes, when Delta format files are present
Security governance Fabric-side permissions required; Unity Catalog policies not inherited Permissions defined on Fabric side; source storage credentials required
Supported table types Managed and external Delta tables only; views and streaming tables excluded Any ADLS, S3, or GCS path with any file format

For teams that need ad hoc access to specific file paths or containers without the overhead of registering catalog metadata, a Shortcut is the simpler choice. For BI teams who need a coherent, discoverable view of an entire Databricks catalog with T-SQL query capability and Power BI Direct Lake support, Mirroring delivers a substantially richer experience out of the box. The two mechanisms are not mutually exclusive, and many organizations employ Shortcuts for engineering tasks and Mirroring for reporting layers simultaneously.

Genuine Limitations That Warrant Careful Planning

Microsoft's official documentation for Azure Databricks Mirroring lists several table types that are not supported, and understanding these exclusions is necessary before committing to Mirroring as the primary integration strategy. Tables governed by row-level security or column-level security policies in Unity Catalog are not eligible for mirroring. Views, materialized views, and streaming tables are similarly excluded. Additionally, Databricks Delta Sharing tables and Lakehouse federated tables cannot be mirrored. This means that organizations whose Databricks estates contain significant governance-sensitive tables, complex view hierarchies, or streaming table architectures will find that Mirroring covers only a subset of what they need to expose.

The security inheritance gap is particularly noteworthy. Unity Catalog permissions, including fine-grained column masking and row filtering policies, do not transfer to Fabric when a catalog is mirrored. Every permission boundary that existed in Databricks must be re-established within the Fabric workspace using OneLake data access roles and Fabric-native RBAC. Organizations that assume Mirroring will preserve their existing governance posture automatically will encounter meaningful security gaps that require deliberate remediation work before the mirrored data can be safely exposed to end users.

Furthermore, the SQL Server Mirroring path introduces its own set of considerations. Because data is physically replicated into OneLake, the initial snapshot for large databases can take considerable time, and the ongoing replication consumes Fabric capacity units in addition to storage. Automated conflict resolution for simultaneous writes is not a concern since the mirrored SQL Analytics Endpoint is strictly read-only, but schema changes on the source SQL Server, such as adding or dropping columns, require Mirroring to handle schema evolution gracefully, which Microsoft's documentation acknowledges is an area of ongoing improvement.

Where Mirroring Delivers Clear Value

Weighing these limitations against the concrete operational benefits, Mirroring offers unarguably successful outcomes in several well-defined scenarios. The elimination of ETL pipelines between SQL Server and Fabric means that BI teams can access near real-time data without the engineering cycles required to build and maintain Azure Data Factory or Fabric Data Factory pipelines. For organizations that have previously relied on nightly batch exports to populate reporting databases, Mirroring reduces reporting lag from hours to seconds while simultaneously removing a class of pipeline failures from the operational support burden.

For Databricks-heavy organizations attempting to extend analytics access to business users who are not comfortable operating within the Databricks workspace interface, Mirroring provides a fruitful bridge. Business analysts accustomed to T-SQL and Power BI can query Databricks Delta tables through the familiar SQL Analytics Endpoint without requiring Databricks user licenses or training. Additionally, Power BI reports built against mirrored Databricks catalogs can take advantage of Direct Lake mode, which delivers substantially lower query latency compared to DirectQuery against Databricks SQL Warehouse endpoints, particularly at scale.

Conclusion

Fabric Mirroring represents a meaningful architectural advancement in reducing the friction between data engineering platforms and analytics consumption layers. The zero-copy approach for Databricks and the zero-ETL incremental replication approach for SQL Server both address real costs that organizations have historically accepted as unavoidable. However, the limitations are equally real. The exclusion of governed tables, views, and streaming table types from Databricks Mirroring, the requirement to re-establish security policies in Fabric, and the storage implications of SQL Server replication all represent constraints that must be incorporated into architecture decisions before deployment. Organizations that assess Mirroring against their specific table inventory and governance requirements before committing will find it a genuinely valuable tool. Those who assume it is a universal solution for all cross-platform data access will encounter meaningful gaps that require supplementary approaches.
